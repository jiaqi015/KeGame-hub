# 我是王牌资产顾问 · 完整方案

最后更新：2026-04-17

这份文档不是只讲一个点。

它要一次讲清楚五件事：

- 这个产品现在到底是什么
- 真正的游戏骨架应该是什么
- 单房主线和整局评分怎么接
- 现有代码已经支撑到哪
- 技术上下一步应该怎么全局改

一句话目标：

- 把这条线从“能玩的经营模拟器”收成一套真正成立的策略游戏

---

## 一句话定义

这是一个在受约束微环境里展开的多盘经营策略游戏。

玩家每开一局，不是在做一组教学动作，也不是在完成任务清单。

玩家是在：

- 有限时间里
- 带着有限精力和推广金
- 面对几套彼此会互相影响的房
- 同时活在一个其他门店也在持续做动作的共享商圈里
- 争夺局势控制权

最后这局打得好不好，不是只看成交几单，而是看：

- 你有没有把房子做得跑赢它们各自所处的盘面
- 你有没有守住关键房
- 业主最后满不满意

---

## 产品本质

这条线本质上不是教学系统。

也不是考试系统。

更不是“卖房百科 + 判断题”。

它的本质是：

- 一局局可重开的
- 以房源组合经营为核心的
- 有环境、有压力、有取舍、有后果的策略游戏

所以设计上必须满足三件事：

1. 玩家要感到“这是一局”
2. 玩家要感到“每套房都值得在意”
3. 玩家要感到“我的每一步都会改变整个盘面”

只要这三件事有一件不成立，这条线就会滑回：

- 模拟器
- 任务器
- 培训器

---

## 核心骨架

整条线以后统一按五层看：

1. 共享市场层
2. 玩家经营层
3. 外部门店层
4. 联动层
5. 结算层

### 1. 共享市场层

共享市场层回答的是：

- 这一局商圈里本来就有什么
- 今天这个商圈又新增了什么
- 玩家和其他门店在争夺什么

它至少包含：

- 市场格子
- 商圈客户池
- 外部竞品盘
- 每日事件导演器
- 临时规则效果

这里最关键的收敛是：

- 事件不再只是“给某套房加减数值”
- 事件首先是“今天整个商圈发生了什么”

所以每日事件系统应该直接隶属于共享市场层。

### 2. 玩家经营层

玩家经营层回答的是：

- 这套房现在是什么局面
- 这套房最后会落成什么样

这里最关键的一句是：

- 每个房源都有自己的主线

玩家真正记住的，不该只是：

- 信任 58
- 热度 63
- D3 72

玩家应该记住的是：

- 这套房快被截走了
- 这套房虽然没卖，但我还没把它做崩
- 这套房值得我继续守
- 这套房得尽快收，不然就要难看了

也就是说，数值是底层，主线才是玩家感受到的对象。

### 3. 外部门店层

外部门店层回答的是：

- 除了玩家之外，还有哪些经营主体在同一个商圈里持续行动
- 他们会如何通过客户、业主和价格锚影响玩家

这里必须明确一件事：

- 竞争不只是玩家手里几套房之间的内部竞争
- 更重要的是玩家与外部门店之间对共享资源的争夺

外部门店应该做轻量模拟，而不是完整玩家镜像。

它们最重要的作用不是“自己也玩一局”，而是对玩家盘面持续施压：

- 抢客户
- 抢窗口
- 提前成交
- 制造价格锚
- 把本来平稳的业主情绪搅乱

### 4. 联动层

联动层以后不只看“我方盘之间互相影响”，而要同时覆盖：

- 我方房与我方房之间
- 我方房与外部竞品之间
- 业主与业主之间
- 市场消息与房源之间
- 玩家资源投入与整盘局势之间

### 5. 结算层

结算层回答的是：

- 这局最后到底打成什么样

正确顺序不是：

- 先看总分
- 再看细项

正确顺序应该是：

1. 先看每套房最后是什么结果
2. 再把这些结果翻译成三轴评分
3. 再给整局总分和评级

也就是说：

- 单房结果在前
- 整局总账在后

---

## 单房主线应该怎么成立

单房主线以后不能只靠：

- `active`
- `sold`
- `withdrawn`

这三个状态撑住。

这三个状态只够做运行时推进，不够做游戏层的结果表达。

单房结果至少要回答四个问题：

1. 有没有结果
2. 结果是不是你做出来的
3. 结果体不体面
4. 业主最后感受如何

### 推荐的单房终局结构

建议以后给每套房补一层正式结算对象，例如：

```ts
type ListingEndingType =
  | 'sold_by_you_happy'
  | 'sold_by_you_neutral'
  | 'sold_by_you_regret'
  | 'sold_by_other'
  | 'not_sold_no_regret'
  | 'not_sold_regret'
  | 'switch_to_rent_no_regret'
  | 'withdrawn_unhappy';

type ListingRelativeOutcome =
  | 'outrun'
  | 'flat'
  | 'lose';

type OwnerSatisfactionState =
  | 'happy'
  | 'neutral'
  | 'no_regret'
  | 'regret'
  | 'unhappy';
```

上面这套不用完全照抄，但意思要成立：

- 运行时状态是一层
- 游戏结算终局是另一层

### 单房终局的接地气解释

不建议给玩家看太抽象的系统名词。

玩家实际看到的可以是这些：

- 卖掉了，很满意
- 卖掉了，无感
- 卖掉了，但体验不好
- 被别家卖掉了
- 没卖掉，但业主不后悔
- 没卖掉，业主开始后悔
- 不卖了，转去出租了，但还能接受
- 彻底做崩了

这才是玩家会记住的房源结局。

---

## 整局评分应该怎么成立

以后整局结算固定走三轴：

1. 能力分 `40`
2. 守盘分 `35`
3. 满意分 `25`

### 1. 能力分

能力分回答的问题是：

- 你把这些房子做得怎么样
- 相对它们各自所处盘面，是跑赢、跑平还是跑输

这条线不是看纯大盘，也不是只看成交数。

它本质上在看：

- 玩家有没有把应该打出来的房真正打出来

能力分的单位应该尽量下沉到单房：

- 这套房跑赢
- 这套房跑平
- 这套房跑输

最后整局只是把这些单房表现加权汇总。

### 2. 守盘分

守盘分回答的问题是：

- 关键房源有没有守住
- 有没有被竞品截走

这条线把“好房不能被隔壁门店卖掉”正式写进了游戏目标。

守盘分不是看总成交，而是看：

- 核心盘是否守住
- 重点盘是否大量失守
- 局末是否还有本该稳住的房被做丢

### 3. 满意分

满意分回答的问题是：

- 业主最后满不满意
- 是满意、无感、后悔还是不满

满意分不只是关系值的平均。

它更像单房终局在“人”的这一面上的翻译。

也就是说：

- 同样都是成交
- 可能一个是满意
- 一个只是无感
- 一个甚至是成交了但体验很差

这三种结算感受应该被明确区分。

---

## 三轴为什么必须从单房结果里长出来

如果三轴直接从总 KPI 算：

- 就会显得硬
- 会逼着玩家只盯总账
- 单房主线就会沦为过程变量

只有从单房结果里长出来，整局评分才会顺。

比如：

- 卖掉了，很满意
  能力、守盘、满意都加

- 卖掉了，但体验不好
  能力和守盘加，满意少加

- 被别家卖掉
  守盘大扣，能力偏低

- 没卖掉，但业主不后悔
  能力不一定高，但满意不差

- 没卖掉，而且开始后悔
  满意明显下滑

- 转租止损
  能力要看盘面，满意不一定差

这样三轴就不是硬凑的指标，而是房源命运的翻译层。

## 盘面目标应该怎么存在

每局都应该有背景目标。

但这个目标不是任务面板。

它是这局的结算语境。

也就是说：

- 三轴评分始终一致
- 每局只是更强调其中哪一轴

### 推荐的背景目标类型

#### 1. 打能力局

这局的背景是：

- 盘面一般
- 但你手上的房并不差
- 重点是你能不能把它们做得比环境更好

主看：

- 能力分

副看：

- 守盘分
- 满意分

#### 2. 打守盘局

这局的背景是：

- 关键房容易被盯上
- 最怕的不是少卖一单
- 而是好房被别人摘走

主看：

- 守盘分

副看：

- 能力分
- 满意分

#### 3. 打满意局

这局的背景是：

- 业主基础更脆
- 不是每套房都非要立刻卖
- 但绝不能把局势做崩

主看：

- 满意分

副看：

- 守盘分
- 能力分

### 背景目标的作用

它不是给玩家发任务。

它是让玩家一开局就知道：

- 这局到底最难的地方在哪
- 这局好看的赢法是什么

## 难度应该怎么理解

难度不是单纯抬参数。

难度真正控制的是：

1. 房源主线有多难收
2. 盘面背景有多恶劣
3. 联动传导有多强
4. 高分结算有多难拿

所以难度差异应该体现在：

- 更容易出现哪些房源终局
- 更常见哪些局面压力
- 玩家更容易在哪条轴上失分

比如：

### 热身 / 入门

更常见：

- 卖掉了，很满意
- 没卖掉，但不后悔

不太常见：

- 被别家截走
- 彻底做崩

### 标准 / 进阶

开始常见：

- 卖掉了，但不算漂亮
- 重点房开始有失守风险
- 不卖也不崩，和卖掉但不舒服会同时出现

### 高压 / 极限

更常见：

- 被竞品抢走
- 来不及全部救
- 有些房只能做成不后悔，而做不成很满意

这时难度才真的是“局面变了”，而不是“数字变高了”。

---

## 随机生成应该生成什么

随机生成不是随机出几套房。

真正要随机的，是一整局盘面。

一局盘面至少要同时生成：

- 房源结构
- 本局背景目标
- 房源之间的联动关系
- 时间和资源压力
- 事件节奏
- 本局更容易出现的终局分布

### 现在生成器已经做对的一半

现在代码里的生成器已经有这些基础：

- 按难度配置初始区间
- 按蓝图生成不同角色房源
- 按蓝图生成竞争结构
- 按事件弧生成脚本事件

这说明它已经不是“随机几组数字”。

方向是对的。

### 还缺的一半

现在生成器还没有直接生成：

- 这套房的结算权重
- 这套房更可能滑向什么终局
- 这局更强调能力、守盘还是满意
- 这局的背景目标说明

也就是说：

- 它已经能生成局面原料
- 但还没有把“为什么这是一局什么味道的局”完整写出来

## 技术上要全局改什么

如果按这套方案继续，技术上最关键的是四块。

### 1. 改领域模型

这是第一刀。

必须在领域层先补正式概念。

建议补这些字段：

#### `ScenarioDefinition`

新增：

```ts
goalContext: 'ability' | 'defense' | 'satisfaction';
targetScore: number;
scoreThresholds: {
  pass: number;
  strong: number;
  ace: number;
};
boardPressureProfile: {
  abilityPressure: number;
  defensePressure: number;
  satisfactionPressure: number;
};
```

#### `Case`

新增：

```ts
goalTier: 'core' | 'important' | 'normal';
endingType?: ListingEndingType;
relativeOutcome?: 'outrun' | 'flat' | 'lose';
ownerSatisfaction?: 'happy' | 'neutral' | 'no_regret' | 'regret' | 'unhappy';
defenseOutcome?: 'held' | 'at_risk' | 'lost_to_rival' | 'withdrawn';
storylineState?: 'healthy' | 'fragile' | 'sliding' | 'critical';
```

这些字段不是装饰。

它们会成为后面：

- 结算
- 派生提示
- UI 展示
- 生成器控制

的统一锚点。

### 2. 改派生层

当前 `updateDerivedState` 负责把运行时状态翻译成玩家看得懂的提示。

以后它要再多做一步：

- 把数值状态翻译成主线状态

也就是不只是给：

- `关系脆弱`
- `窗口逼近`

还要能给：

- `正在滑向被截走`
- `这套房已经从可守，滑到高危`
- `虽然没卖，但当前仍有机会收成不后悔`

这一步是把模拟层翻译成游戏感的关键。

### 3. 改结算层

这是第二刀。

不是一上来重写所有引擎，而是先把结算骨架钉住。

建议顺序：

1. 先实现单房终局判定
2. 再从单房终局汇总三轴
3. 再从三轴汇总总分
4. 最后输出目标分和评级

建议新增一个专门的结算模块，比如：

- `domain/finalization.ts`
- 或 `domain/resultEvaluation.ts`

避免把所有逻辑继续堆在 `engine.ts` 里。

### 4. 改生成器

这是第三刀。

生成器以后不只负责造“能跑的局”，还要负责造“有目标语境的局”。

建议新增生成信息：

- `goalContext`
- `targetScore`
- `goalTier`
- `boardPressureProfile`
- `listing ending tendency`

第一阶段不用把所有终局都直接写死。

只要先把这些房的：

- 权重
- 压力
- 更容易失分的方向

写出来，就已经足够支撑评分和 UI。

## UI 应该怎么改

UI 不是现在第一优先级，但方向要先定。

### 1. 开局页

开局页以后要明确三件事：

- 这局是什么局
- 主要看哪一轴
- 目标分是多少

玩家点进来，应该立刻知道：

- 这局是打能力、打守盘，还是打满意

### 2. 局内首页

首页以后最重要的不是平均数值，而是：

- 本局三轴目前大概什么状态
- 今天最危险的是哪条主线
- 今天最值得救的是哪套房

### 3. 房源页

房源页以后不能只展示参数和按钮。

要让玩家看见：

- 这套房当前主线是什么
- 这套房更可能往哪种结果滑
- 哪种动作是在救它，哪种动作是在赌它

### 4. 结算页

结算页以后必须按这个顺序来：

1. 每套房最后怎么样
2. 三轴分别得了多少
3. 整局有没有过目标分
4. 这局是什么赢法，或者输在哪

只有这样，结算才会真正像一局游戏的收官。

## 推荐实现顺序

这里给一条最稳的落地顺序。

### 第一步

先补正式领域模型：

- 单房终局
- 三轴输入
- 本局目标语境
- 房源分层

### 第二步

重写结算逻辑：

- 先单房
- 后三轴
- 再总分

### 第三步

改结算页：

- 先显示每套房的收尾
- 再显示三轴解释

### 第四步

改派生提示：

- 从风险提示升级到主线提示

### 第五步

改生成器：

- 让每局不仅有结构
- 还有更明确的目标味道

这条顺序的好处是：

- 先把骨架钉住
- 再改体验表达
- 最后再把生成器完全吃进来

风险最低。

## 一句收束

这条线现在已经不是“要不要做成游戏”的问题了。

代码已经站在游戏这边了。

现在真正要做的，是把它从：

- 一套多盘日推进经营模拟

推进成：

- 一套每个房源都有主线
- 所有主线活在同一个微环境里
- 玩家每一步都在改写局势
- 最后用能力分、守盘分、满意分收束整局后果

如果这步做成，这条线才会真正从“功能集合”变成“完整游戏”。
## 运行时对象收敛

从运行时架构看，整局以后不要只围绕 `cases` 展开。

最少应收敛成下面五类对象：

- `cases`
  玩家正在经营的房
- `rivalListings`
  商圈里不归玩家经营、但会持续施压的外部竞品盘
- `sharedDemandPool`
  可被多家门店争夺的客户和需求流
- `dailyEvent`
  今天整盘局面的主事件
- `activeRuleEffects`
  今日或本周生效的临时规则

这样以后“新竞品入场”“老业主转介绍一套急盘”“客户集体观望”“本周推广金拨付缩减”这类东西，才有明确的架构落点。

## 设计主轴的收敛句

这条线以后统一按下面这句话推进：

- 玩家不是唯一经营者
- 房不是孤立对象
- 客户不是玩家私有资源
- 每天的局面变化来自玩家动作、其他门店动作和市场事件共同作用

只有这句话成立，这游戏才真正像一盘会反扑、会失守、会留下后果的经营局。
