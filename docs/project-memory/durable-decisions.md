# 稳定决策

最后整理：2026-04-17

这份文件只保留“跨线程仍然成立”的决策。阶段性推进项请看 [当前焦点](current-focus.md)。

## 产品层

- 仓库层面已经是统一入口项目，不再把“开放日”当成整个站点的唯一身份。
- 对外产品文案允许继续演进，但内部代码里的 `open-day` 命名暂时不做大规模重命名。
- `多模型PK`、`开放日选址`、`我是王牌资产顾问` 三条业务线应继续被视为同一产品家族，而不是三个互不相关的孤岛。

## 开放日选址

- 用户主流程保持“两步式”，不回退成把上传、配置、结果全部塞在同一个大页面里。
- 参数体系必须继续区分：
  - 默认值
  - 可调值
  - 分位表达
  - 绝对值表达
- 参数覆写是主能力，不是附属配置。
- 测算应由明确动作触发，避免用户一改参数前端就无控制地自动重算。
- 公式、参数包、历史快照、方案模板、方案版本等能力属于工作台核心能力，不应被弱化成一次性辅助功能。

## 架构层

- 项目整体继续保持前后端分离思路。
- 开放日逻辑继续按领域服务、仓储、缓存、接口分层演进，而不是重新堆回页面组件。
- 能通过服务端解析缓存、结构化持久化、上传归档解决的问题，优先在服务端解决。
- `modules/open-day/` 代表开放日领域化方向，应继续作为核心落点，而不是重新回到 `legacy` 实现。

## 基础设施层

- 当 `DATABASE_URL` 或 `POSTGRES_URL` 存在时，优先使用 `Neon Postgres` 做结构化持久化。
- 当运行在 Vercel 且能力可用时，可优先使用 Runtime Cache 与 Blob。
- 本地开发允许回退到文件或内存实现，不要求本地强依赖云资源。

## 资产顾问玩法

- 数据模型不能停留在单个 `run + save_data` 的粗粒度存档。
- 当前稳定的业务抽象主轴仍然是：
  - `业主画像`
  - `房源阶段`
  - `好房分`
- 运行层应覆盖整局、房源、事项、交互事件，而不是只堆叠数值按钮。
- 每个动作最终都应能映射到“有来有回的交互模板”，并沉淀为结果。
- “关联机会”语义应继续往“准客池”靠拢，强调经营视角，而不是退回传统 CRM 列表视角。
- 房源详情页的组织方式应围绕经营判断，而不是属性平铺。稳定观察面包括：
  - 这套盘是谁
  - 这个业主怎么样
  - 这套货能不能打
  - 这套盘的准客池厚不厚
  - 这周我得处理什么
- 房源详情页动作区继续采用双层结构：
  - `建议动作` 负责表达当前主矛盾下的优先级
  - `全部动作` 负责表达当前可做、不可做及其原因
- `首次面访` 不能由任意触达动作隐式替代，必须保持独立完成状态；业主触达状态也必须与通用动作触达分开建模。

## 协作与记忆

- 优先保留仓库内可读文档，而不是把关键背景只留在对话里。
- 自动生成的记忆可以作为线索，但不能未经整理直接当权威事实。
- 协作恢复时，优先读取：
  - 仓库内 `MEMORY.md`
  - `docs/project-memory/`
  - 然后再看 Codex 私有恢复材料
