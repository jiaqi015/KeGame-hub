# 稳定决策

最后整理：2026-04-17

## 产品与命名

- 仓库层面是统一入口项目，不再把“开放日”当成整个站点的唯一身份。
- 对外产品文案可以继续调整，但内部代码中的 `open-day` 命名暂时保留，避免一次性重命名带来高风险。
- “关联机会”在资产顾问玩法里应向“准客池”语义靠拢，强调经营视角，而不是单纯 CRM 列表视角。

## 开放日选址

- 用户主流程采用两步式，而不是把上传、配置、结果全部塞在一个页面里。
- 参数必须区分：
  - 默认值
  - 可调整值
  - 分位表达
  - 绝对数值表达
- 参数覆写能力是核心能力，不是边角配置。
- 公式、参数包、历史快照、方案模板都属于工作台主能力，后端需要继续承担目录化和持久化职责。
- 测算应尽量避免前端“自动乱跑”，用户调整后由明确的“测算”动作触发。

## 架构方向

- 项目整体应继续保持前后端分离思路。
- 开放日模块按领域服务/仓储/缓存思路扩展，而不是把逻辑重新堆回页面组件。
- 能通过服务端缓存、上传归档、解析缓存解决的耗时问题，优先在服务端解决。
- 当 `DATABASE_URL / POSTGRES_URL` 存在时，优先使用 `Neon Postgres` 做结构化持久化。
- 当运行在 Vercel 上时，可优先使用 Runtime Cache 与 Blob，开发环境允许回退到本地文件或内存实现。

## 资产顾问玩法

- 数据模型不应只停留在 `run + save_data` 的粗粒度存档。
- 当前已经稳定的抽象主轴是：
  - `业主画像`
  - `房源阶段`
  - `房源竞争力`
- 运行层需要覆盖：
  - 整局
  - 房源
  - 事项
  - 交互/事件
- 每个动作本质上都应该能映射到“有来有回的交互模板”，最后沉淀结果。
- 房源详情页的组织方式应围绕经营问题，而不是属性平铺。稳定的五个观察面是：
  - 这套盘是谁
  - 这个房东怎么样
  - 这套货能不能打
  - 这套盘的准客池厚不厚
  - 这周我得处理什么

## 工程习惯

- 优先保留仓库内可读文档，而不是把关键背景只留在对话里。
- 自动生成的记忆可以作为线索，但不能未经整理直接当权威事实。
- 面向后续协作时，项目内 `MEMORY.md` 与 `docs/project-memory/` 应作为第一入口。
