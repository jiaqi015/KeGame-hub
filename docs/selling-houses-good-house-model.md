# 卖房（资产顾问）好房模型设计

这份文档回答一个问题：

> “好房分”到底怎么来，三维度到底各算什么。

这里的“好房模型”不是前端展示技巧。
也不是把几个 case 字段一加权。

它应该是一个独立的客观评估器。

---

## 0. 一句话结论

好房模型回答的是：

> 在今天这个市场、这个价格、这个业主配合度下，这套房整体到底有多好卖。

我建议保留三维：

1. `D1 准客池`
2. `D2 房屋吸引力`
3. `D3 业主意愿`

然后再聚合成：

- `goodHouseScore`
- `goodHouseLevel`
- `goodHouseReasonTags`

---

## 1. 这个模型不该做什么

好房模型不该做 4 件事：

1. 不替代价格模型。
2. 不替代机会推进概率。
3. 不直接告诉玩家“现在去做什么”。
4. 不把客户单次情绪波动误当成房子的客观质量。

也就是说：

- 它是房源层面的“卖相评估”
- 不是某一条机会的“成交概率”

## 2. 输入和输出

## 2.1 输入

| 输入组 | 主要字段 | 作用 |
| ------ | -------- | ---- |
| `CaseProfile` | 板块、户型、面积、装修、标签、缺点 | 决定房子天然卖相 |
| `CaseRuntime` | 热度、曝光、竞品压力、挂牌状态 | 决定房子当前表现 |
| `OwnerCaseRelation` | 信任、耐心、紧迫度、是否接受开放日、是否接受调价 | 决定业主配不配合 |
| `PriceModelOutput` | 挂牌价、心理价、市场估价、价差、价格可行度 | 决定价格是否卡住 |
| `MarketModel` | 区域需求、总价带流动性、周节奏 | 决定市场给不给力 |
| `CustomerCaseRelation[]` | 活跃关系数、有效关系数、各阶段分布 | 用来估算准客池厚度 |
| `PlatformCaseCustomerMatch[]` | 平台基于客户画像算出的房客匹配结果 | 用来估算全 ACN 的潜在准客规模 |

## 2.2 输出

| 输出 | 含义 |
| ---- | ---- |
| `d1CustomerPool` | 准客池厚不厚 |
| `d2Attractiveness` | 房子本身有没有吸引力 |
| `d3OwnerReadiness` | 业主愿不愿意配合卖 |
| `goodHouseScore` | 综合结果，0-100 |
| `goodHouseLevel` | 分档，如偏弱、一般、较好、强 |
| `goodHouseReasonTags` | 为什么高，为什么低 |

## 3. 三维的定义

## 3.1 D1：准客池

一句话：

> 市场里到底有没有足够多“买得起、看得上、愿意推进”的客户。

### D1 看什么

| 子项 | 说明 |
| ---- | ---- |
| 潜在客户覆盖度 | 预算能覆盖这套房的人多不多 |
| 板块需求匹配度 | 想在这里买的人多不多 |
| 户型需求匹配度 | 这类房型是不是有人接 |
| 平台匹配规模 | 全 ACN 客户画像里有多少客户和这套房匹配 |
| 可触达规模 | 匹配客户里有多少能通过合规方式触达 |
| 当前有效活跃关系数 | 不是所有 relation 都算，只算还活着的 |
| 关系质量 | 当前这些 relation 的 intent、confidence、阶段深度怎么样 |
| 客户注意力竞争 | 同一批客户是不是被别的房子强烈分流 |

### D1 不看什么

1. 单个客户当天心情。
2. 业主是否强势。
3. 玩家今天有没有点某个按钮。

这些会影响推进，但不是准客池本体。

这里还要补一条市场量级事实：

> 客户总体量很大，不代表这套房就容易成交。

像北京这样的市场，可以粗理解成：

- 出售中房源量级大约 10 万
- 月成交量级大约 1.5 万
- 客户体量大约是房源的 10 到 20 倍
- 但客户决策周期很长

所以 D1 不能简单理解成“客户越多越好”。
更准确的是：

- 潜在客户多，说明这套房有池子
- 但客户决策慢，说明池子不等于成交
- 真正有价值的是可触达、可推进、愿意持续看的客户池

### D1 建议拆成 6 个子分

| 子分 | 建议权重 | 说明 |
| ---- | -------- | ---- |
| 预算覆盖度 | 20% | 先看买不买得起 |
| 需求匹配度 | 20% | 再看想不想买这类房 |
| 平台匹配规模 | 20% | ACN 客户画像里有多少潜在适配客户 |
| 有效关系量 | 15% | 现在池子里有多少活机会 |
| 关系质量 | 15% | 这些机会是不是浅关系 |
| 注意力稳定度 | 10% | 会不会很容易被别的盘吸走 |

建议公式：

```text
D1 =
  0.20 * budgetCoverage
+ 0.20 * demandCoverage
+ 0.20 * platformMatchScale
+ 0.15 * activeRelationDepth
+ 0.15 * relationQuality
+ 0.10 * attentionStability
```

### D1 里的平台匹配，不等于客户公开

这里要特别注意：

同 ACN 内房源公开，但客户不是公开的。

平台可以用客户画像和房源做全量匹配，算出：

- 潜在客户数
- 高匹配客户数
- 可合规触达客户数
- 房源机会分

但这些只是后台计算和匿名统计。
它不代表每个经纪人都可以看到别人的客户明细。

还要注意：

同一个真实客户可能同时找多个经纪人。
平台后台可以识别重叠客户，但前台不应该把别人的客户明细暴露出来。

所以 D1 里的客户规模要做去重或折损：

- 同一真实客户被多个经纪人维护，不能重复当成多个客户
- 多经纪人咨询越强，客户注意力越分散
- 对房源来说，这会提高潜在规模，但也提高抢客和归因风险

具体客户要进入推进漏斗，仍然要通过：

- 客户主动咨询
- 维护经纪人推荐
- 转介
- 商圈经理协调
- 其他合规协作事项

## 3.2 D2：房屋吸引力

一句话：

> 这套房站在市场里，本身有没有让客户愿意来看、愿意继续看的能力。

### D2 看什么

| 子项 | 说明 |
| ---- | ---- |
| 板块吸引力 | 区域是不是受欢迎 |
| 房型适销性 | 户型是不是主流好卖型 |
| 产品竞争力 | 面积、朝向、楼层、装修、景观这些综合如何 |
| 标签卖点强度 | 学区、地铁、次新、稀缺、总价带优势等 |
| 缺点惩罚 | 噪音、楼层短板、采光问题、总价过高等 |
| 曝光表现 | 最近有没有足够被看到 |
| 竞品压力 | 同类盘是不是更强 |
| 相似房源重叠度 | 命中同需求、同预算客户的相似房源是不是很多 |

### D2 不看什么

1. 业主配不配合。
2. 客户买不买得起。
3. 谈价谈得顺不顺。

这些分别属于 D3、relation、价格模型。

这里要补一个竞争事实：

> 越相似的房源，竞争越激烈。

相似不是只看“同一个小区”。
更重要的是：

- 命中的客户需求是否相似
- 命中的预算带是否相似
- 户型段是否相似
- 商圈是否相似

所以：

- 同小区相似房，竞争往往最直接
- 同商圈、同预算带、同户型段的房，也会强烈竞争
- 房源竞争强度本质上来自客户重叠度

### D2 建议拆成 6 个子分

| 子分 | 建议权重 | 说明 |
| ---- | -------- | ---- |
| 区域吸引力 | 15% | 市场环境加成 |
| 房型适销性 | 20% | 产品类型是否对路 |
| 物理产品力 | 20% | 房子本身硬素质 |
| 卖点标签强度 | 20% | 有没有明确卖点 |
| 曝光与到访表现 | 15% | 最近是不是有人看见 |
| 缺点与竞品惩罚 | 10% | 用负向扣分控制 |

建议公式：

```text
D2 =
  0.15 * areaAppeal
+ 0.20 * layoutLiquidity
+ 0.20 * productQuality
+ 0.20 * sellingPoints
+ 0.15 * exposurePerformance
+ 0.10 * (100 - penaltyScore)
```

## 3.3 D3：业主意愿

一句话：

> 这套房的业主，当前是不是愿意和你一起把这套房卖出去。

### D3 看什么

| 子项 | 说明 |
| ---- | ---- |
| trust | 对经纪人的信任 |
| patience | 对出售过程的耐心 |
| urgency | 这套房要不要尽快卖 |
| priceFlexibility | 对调价、对报价的松动度 |
| actionCooperation | 是否配合开放日、反馈、带看、照片、整理房子 |
| strategyAlignment | 是否认同当前出售路径 |

### D3 不看什么

1. 房子客观好不好。
2. 客户有没有钱。
3. 市场热不热。

这些最多作为背景输入，不该直接吞掉 D3 的主体含义。

### D3 建议拆成 6 个子分

| 子分 | 建议权重 | 说明 |
| ---- | -------- | ---- |
| 信任度 | 25% | 你能不能推进动作的前提 |
| 耐心度 | 15% | 会不会轻易撤盘或失去合作意愿 |
| 紧迫度 | 15% | 有无出售动力 |
| 价格松动度 | 20% | 能不能回到成交区间 |
| 配合度 | 15% | 能不能把动作落下去 |
| 路线认同度 | 10% | 接不接受你的打法 |

建议公式：

```text
D3 =
  0.25 * trust
+ 0.15 * patience
+ 0.15 * urgency
+ 0.20 * priceFlexibility
+ 0.15 * actionCooperation
+ 0.10 * strategyAlignment
```

## 4. 综合分怎么算

### 4.1 先算三维

先分别算出：

- `D1`
- `D2`
- `D3`

### 4.2 再聚合成好房分

建议先沿用你已有的权重语义：

```text
goodHouseScore =
  0.40 * D1
+ 0.35 * D2
+ 0.25 * D3
```

这个权重的直觉是：

1. 没有客户池，再好的房也很难卖。
2. 房子本身吸引力是第二层核心。
3. 业主配合很重要，但它更像放大器，不是全部。

### 4.3 再做分档

| 分数 | 档位建议 | 业务理解 |
| ---- | -------- | -------- |
| 0-54 | 偏弱 | 难卖，问题明显 |
| 55-67 | 一般 | 有机会，但比较吃动作 |
| 68-77 | 较好 | 具备经营基础 |
| 78-87 | 强 | 推进条件不错 |
| 88-100 | 很强 | 属于明显好卖的房 |

## 5. reason tags 怎么出

分数够不够还不够。
玩家还要知道为什么。

所以建议每次输出时同时给出：

- `positiveReasons[]`
- `negativeReasons[]`

例子：

| 标签 | 来源 |
| ---- | ---- |
| 刚需总价带有优势 | D1 / D2 |
| 区域近两周带看热度高 | D1 / Market |
| 户型主流、卖点清晰 | D2 |
| 同类竞品偏多 | D2 负项 |
| 业主信任高，愿意配合开放日 | D3 |
| 价格还高于市场估值 | PriceModel 负项 |

这样前端才能做“为什么是这分”。

## 6. 什么时候重算

## 6.1 不用每一秒重算

推荐两层：

1. 白天局部更新时，脏掉相关 case 的缓存。
2. 日结时统一重算所有活跃 case。

## 6.2 哪些事会触发局部重算

1. 挂牌价变化。
2. 业主关系变化。
3. 市场事件命中这套房。
4. 有效关系数明显变化。
5. 开放日、推广、带看完成后曝光和反馈变化。

## 7. 和 PriceModel、Relation 的边界

### 7.1 和 PriceModel 的边界

- `PriceModel` 负责算价格站不站得住。
- `GoodHouseModel` 负责算这套房整体好不好卖。

价格不合理会拖低好房分。
但价格模型本身不要被吃掉。

### 7.2 和 Relation 的边界

- `CustomerCaseRelation` 算的是某个客户和这套房的推进。
- `GoodHouseModel` 算的是这套房整体对市场是不是有卖相。

一个是微观机会。
一个是房源总体。

## 8. 一个完整例子

假设一套房：

- 在主流刚需板块
- 户型好，装修可接受
- 挂牌价略高于市场
- 业主信任你，但对调价还犹豫
- 当前有 8 个有效客户关系，其中 2 个已到复看

那么可以这样理解：

- `D1` 较高
  因为准客池厚，而且有较深机会
- `D2` 较高
  因为产品本身有竞争力，但价格略拖后腿
- `D3` 中上
  因为信任不错，但价格松动度还没完全打开

最后 `goodHouseScore` 很可能在 75-82 区间。

这类房的经营重点就不是“从 0 到 1 找客户”，
而是“把价格和业主配合度往成交区间再推一步”。

## 10. 一句话结论

好房分最重要的不是“算一个数”，
而是把下面三件事分开：

1. 有没有客。
2. 房子本身行不行。
3. 业主愿不愿意配合卖。

只要这三件事分得清，后面动作、复盘、结果页都会顺很多。
