# 卖房（资产顾问）经纪公司、品牌与 ACN 架构

这份文档补一个很关键的点：

> 经纪公司不是一个简单的“公司压力”字段。经纪公司本质上有品牌，每个品牌内部有自己的 ACN 协作网络。

如果不把这层建出来，后面会有几个东西讲不清：

1. 为什么同一个市场里，有些经纪人是合作关系，有些是竞争关系。
2. 为什么房源、客户、线索、成交不是只属于一个经纪人。
3. 为什么品牌会影响客户信任、房源流通、门店动作和竞品压力。
4. 为什么“竞品”不能只是一个 `Rival` 数字。

---

## 0. 一句话结论

组织层建议这样建：

```text
BrokerageCompany
  -> Brand
    -> ACN
      -> Store
        -> BizAreaManager
        -> Broker
```

其中：

- `BrokerageCompany`：经纪公司主体
- `Brand`：品牌，是客户感知和市场信任的外壳
- `ACN`：品牌内部的经纪人协作网络
- `Store`：门店，是组织经营单元
- `BizAreaManager`：商圈经理，管理一组经纪人
- `Broker`：经纪人，是玩家或 NPC 执行动作的人

## 0.5 业务事实

这一节不是设计偏好。
是目前已经确认、后面不应该再来回摇摆的业务事实。

### 组织事实

1. 经纪公司本质上有品牌。
2. 每个品牌内部有自己的 ACN。
3. 商圈里有商圈经理，管理一组经纪人。
4. 经纪人归属于门店、品牌、ACN，也受商圈经理管理。

### 房源与客户事实

1. 同一个 ACN 内，房源是互相公开的。
2. 同一个 ACN 内，经纪人都可以带自己的客户去看公开房源。
3. 客户不是公开池，客户不是 ACN 公共资源。
4. 客户是经纪人维护的私有关系资产，不是品牌内完全共享资源。
5. 一个真实客户可以同时找多个经纪人。
6. 这些经纪人彼此默认不知道对方也在跟这个客户。

### 联卖事实

1. 同一个 ACN 内，本质是联卖网络，不是纯竞品关系。
2. 联卖必须区分房源端和客源端。
3. 房源端负责维护房源和业主。
4. 客源端负责带来客户和推进成交。
5. 同 ACN 内别人带客户成交你的房源，不能简单算“被竞品打败”。
6. 同 ACN 内的成交，要先做房源端/客源端归因，再谈结果好坏。

### 竞争事实

1. 不同品牌之间，才是明确竞争关系。
2. 你的房源被其他品牌成交，算丢盘。
3. 你的客户被其他品牌成交，算丢客。
4. 品牌在商圈内有市场占有率。
5. 市场占有率会影响客户信任、业主信任、房源流通效率和管理压力。
6. 越相似的房源，竞争越激烈。
7. 相似的本质，不只是长得像，而是命中同一批需求、同一批预算的客户。
8. 同小区相似房源，竞争通常最直接。
9. 同商圈、同总价带、同户型段的房源，也会形成强竞争。
10. 房源竞争强度，本质上来自客户重叠度，而不只是地理距离。

### 平台事实

1. 平台可以基于客户画像和所有房源做全量匹配计算。
2. 平台可以算每套房的潜在客户规模、高匹配客户规模和机会分。
3. 平台“可算”不等于经纪人“可见”。
4. 平台后台可以识别多个客户关系是否指向同一个真实客户。
5. 平台后台识别不等于把客户明细公开给所有经纪人。

### 市场量级事实

1. 以北京为例，出售中的房源量级大约是 10 万套。
2. 每个月真实成交量级大约是 1.5 万套。
3. 这意味着市场不是“有没有房”，而是“谁能在竞争中成交”。
4. 客户总体量级大约是房源的 10 到 20 倍。
5. 但客户不是短平快成交，客户决策周期通常很长。
6. 所以这是一个高库存、高客户量、长决策周期、低月成交率的竞争游戏。
7. 客户多，不代表容易成交；真正稀缺的是有效推进和最终成交。
8. 房源竞争的核心，不是缺客户，而是抢客户注意力、抢带看、抢出价、抢成交窗口。

### 设计含义

基于这些业务事实，后面的设计必须满足：

1. 房源公开和客户私有要同时成立。
2. 真实客户主体和经纪人维护关系要分开。
3. 房源端、客源端、联卖归因要能算清楚。
4. 品牌竞争和 ACN 内协作不能混成一个概念。
5. 平台后台能力和前台权限边界必须分开。
6. 房源竞争不能只按“小区是不是一样”判断，还要按客户重叠度来判断。
7. 小区、商圈、总价带、户型段，都应该进入相似房源竞争计算。
8. 系统不能把客户量简单等同于成交效率。
9. 引擎必须能表达“客户很多，但推进很慢，成交更少”。
10. 日结和评分里都要体现长决策周期和低月成交率。

## 1. 为什么 Company 和 Brand 要分开

经纪公司和品牌不是一个东西。

### BrokerageCompany

公司回答的是：

> 背后是谁在经营这一套业务。

它更偏组织和经营层：

- 资源投入
- 管理制度
- 目标压力
- 数据能力
- 训练体系
- 品控体系

### Brand

品牌回答的是：

> 客户和业主在市场上认不认这个招牌。

它更偏市场感知层：

- 品牌信任
- 服务承诺
- 客户认知
- 业主安全感
- 市场口碑
- 对外曝光能力

所以公司可以拥有多个品牌。
每个品牌可以有自己的打法、口碑和 ACN。

## 2. ACN 是什么

ACN 不是一个普通团队。

它本质上是：

> 一个品牌内部，围绕房源、客户、经纪人、门店形成的联卖网络和分佣规则。

它解决的是：

1. 谁可以看见哪些房源。
2. 谁可以合作推进哪些客户。
3. 谁带看、谁维护、谁成交时怎么分工。
4. 内部合作和内部竞争怎么平衡。
5. 门店和经纪人之间怎么共享机会。

更具体地说：

> 同一个 ACN 内，房源是联卖的。每一次成交都要分清“房源端”和“客源端”。

所以 ACN 里不是简单的“谁赢谁输”，而是：

- 房源端：谁维护这套房、谁拿了业主授权、谁负责房源质量
- 客源端：谁带来了客户、谁推进客户、谁最终促成成交

同一个 ACN 内，别人用你的房源成交，不能简单算“被竞品打败”。
但如果你的房源被别人作为客源端成交，而你没有拿到应有的房源端收益或维护价值，就应该算“房源端被动”。

不同品牌之间，才是更明确的竞争关系。

这里要补一个非常重要的边界：

> 同 ACN 内，房源是互相公开的；客户不是公开的，客户是经纪人私有维护资产。

也就是说：

- 同 ACN 经纪人都可以看到房源，并带自己的客户去看
- 但不能随便看到别人的客户明细
- 不能随便触达别人的客户
- 平台可以基于客户画像做计算，但前台只给合理的规模、分数和线索提示

还要再补一层现实：

> 一个真实客户，可能同时找多个经纪人；这些经纪人互相不知道。

所以“客户私有”不是说客户这个人只能属于一个经纪人。
而是说：

- 每个经纪人只知道自己维护到的那条客户关系
- 同一个真实客户可以有多条 `BrokerCustomerRelation`
- 经纪人前台互相不可见
- 平台后台可以识别重叠客户、做去重和风险判断

所以 ACN 的公开对象是房源，不是客户。

所以 ACN 不应该建成 `Actor`。

更准确的是：

- `Brand` 是组织主体
- `Store / Broker` 是行动主体
- `ACN` 是品牌内部的网络规则和协作环境

## 3. 新的组织层对象

## 3.1 BrokerageCompany

公司该放：

| 字段 | 含义 |
| ---- | ---- |
| companyId | 公司 id |
| name | 公司名 |
| managementStyle | 管理风格 |
| dataCapability | 数据能力 |
| trainingCapability | 培训和赋能能力 |
| pressurePolicy | 目标压力方式 |
| brandIds | 旗下品牌 |

公司不该放：

1. 某个客户对某套房的意向。
2. 某个业主对某个经纪人的信任。
3. 某个门店今天的具体执行结果。

这些都在更低层。

## 3.2 Brand

品牌该放：

| 字段 | 含义 |
| ---- | ---- |
| brandId | 品牌 id |
| companyId | 所属公司 |
| name | 品牌名 |
| reputation | 市场口碑 |
| ownerTrustBase | 业主天然信任基线 |
| customerTrustBase | 客户天然信任基线 |
| exposurePower | 品牌曝光能力 |
| serviceStandard | 服务标准 |
| acnId | 品牌内部 ACN |

品牌会影响：

1. 业主是否愿意授权。
2. 客户是否愿意留资。
3. 房源曝光基础能力。
4. 同品牌内部协作效率。
5. 跨品牌竞争压力。

## 3.3 ACN

ACN 该放：

| 字段 | 含义 |
| ---- | ---- |
| acnId | ACN id |
| brandId | 所属品牌 |
| cooperationRules | 合作规则 |
| listingVisibilityRules | 房源公开规则 |
| customerPrivacyRules | 客户私有规则 |
| platformMatchingRules | 平台匹配计算规则 |
| commissionSplitRules | 分佣规则 |
| conflictRules | 撞客、撞盘、冲突处理规则 |
| referralRules | 转介规则 |
| collaborationEfficiency | 协作效率 |
| internalCompetitionLevel | 内部竞争强度 |
| listingSideRules | 房源端规则 |
| customerSideRules | 客源端规则 |
| coSaleRules | 联卖规则 |
| lostListingRules | 丢盘判定规则 |

ACN 会影响：

1. 房源能不能被同品牌门店共同推广。
2. 经纪人能不能带自己的客户看同 ACN 房源。
3. 平台能不能基于客户画像计算房源准客规模。
4. 一个机会失败后，是否有合规的转介或接力机制。
5. 玩家动作是否能借力门店和品牌网络。
6. 内部竞争会不会抢走机会。

ACN 里最核心的业务身份是两类：

| 身份 | 含义 |
| ---- | ---- |
| 房源端 | 维护房源、服务业主、拿到房源授权的一侧 |
| 客源端 | 带来客户、推进客户、完成看房和出价的一侧 |

一个 broker 可以在 A 房上是房源端，在 B 房上是客源端。
所以这个角色一定要挂在 `BrokerCaseRole` 或成交事件上，不能只挂在 `Broker` 自己身上。

## 3.4 Store

门店该放：

| 字段 | 含义 |
| ---- | ---- |
| storeId | 门店 id |
| brandId | 所属品牌 |
| acnId | 所属 ACN |
| bizArea | 主经营商圈 |
| managerPolicy | 店长管理风格 |
| trafficPower | 门店自然流量能力 |
| localKnowledge | 本地市场熟悉度 |
| cooperationCulture | 店内协作文化 |
| managerIds | 该门店或商圈下的管理者 |

门店会影响：

1. 商圈内线索量。
2. 开放日动员能力。
3. 房源维护质量。
4. 经纪人之间是否愿意协作。

## 3.5 BizAreaManager

商圈经理是组织里的管理角色。

他不是市场环境。
他也不是普通经纪人。

他回答的是：

> 这个商圈里，谁来管理一组经纪人，分配目标，协调联卖，推动房源和客户经营。

### BizAreaManager 该放什么

| 字段 | 含义 |
| ---- | ---- |
| managerId | 商圈经理 id |
| brandId | 所属品牌 |
| acnId | 所属 ACN |
| storeIds | 管理哪些门店 |
| bizArea | 管理哪个商圈 |
| brokerIds | 管理哪些经纪人 |
| managementStyle | 管理风格 |
| targetPressure | 目标压力 |
| coordinationSkill | 联卖协调能力 |
| listingDefenseSkill | 保盘能力 |
| customerDispatchSkill | 客源分配能力 |
| coachingSkill | 带教能力 |

### BizAreaManager 会影响什么

1. 经纪人每天做事的优先级。
2. 房源端和客源端怎么协作。
3. 线索怎么分配给经纪人。
4. 哪些房源要重点保盘。
5. 哪些客户要转给更适合的人推进。
6. 品牌在该商圈的市场占有率。

### BizAreaManager 不该放什么

1. 某个客户对某套房的意向。
2. 某个业主对某个经纪人的信任。
3. 某套房的挂牌价。

这些都在更具体的主体或关系上。

## 3.6 Broker

经纪人除了原有字段，还要补组织归属：

| 字段 | 含义 |
| ---- | ---- |
| brokerId | 经纪人 id |
| storeId | 所属门店 |
| brandId | 所属品牌 |
| acnId | 所属 ACN |
| managerId | 所属商圈经理 |
| role | 玩家 / NPC / 竞品经纪人 |
| personalReputation | 个人口碑 |
| cooperationStyle | 协作风格 |
| clientHandlingSkill | 客户推进能力 |
| ownerHandlingSkill | 业主维护能力 |
| ownerPortfolioIds | 当前维护的业主池 |
| customerPortfolioIds | 当前维护的客户池 |

经纪人维护的是“一组关系”，不是把业主和客户变成自己的字段。

所以：

- 经纪人维护业主，用 `BrokerOwnerRelation`
- 经纪人维护客户，用 `BrokerCustomerRelation`
- 经纪人维护房源，用 `BrokerCaseRole`

这些关系里要记录维护深度、信任、最近触达和是否主控。

## 4. 关系怎么建

## 4.1 组织归属关系

| 关系 | 含义 |

| `StoreBrokerRelation` | 经纪人属于门店 |
| `AcnBrokerMembership` | 经纪人属于某 ACN |
| `ManagerBrokerRelation` | 商圈经理管理经纪人 |

## 4.2 业务协作关系

| 关系 | 含义 |
| ---- | ---- |
| `BrokerCaseRole` | 经纪人在某套房上是什么角色 |
| `BrokerOwnerRelation` | 经纪人维护某个业主 |
| `BrokerCustomerRelation` | 经纪人与客户的关系 |
| `AcnListingVisibility` | 某套房在 ACN 内公开可见 |
| `CustomerPrivacyScope` | 某客户归谁维护、谁可见、谁可触达 |
| `PlatformCaseCustomerMatch` | 平台基于客户画像算出的房客匹配结果 |
| `BrokerCooperationRelation` | 两个经纪人之间是否协作顺畅 |
| `CoSaleRelation` | 一次联卖里房源端和客源端如何分工 |

## 4.3 经纪人维护池

经纪人不是直接“拥有”业主和客户。

更准确的是：

> 经纪人维护一批业主关系和客户关系。

### BrokerOwnerRelation

这条关系回答：

> 这个经纪人和这个业主之间，现在维护得怎么样。

建议字段：

| 字段 | 含义 |
| ---- | ---- |
| `brokerId` | 哪个经纪人 |
| `ownerId` | 哪个业主 |
| `maintenanceLevel` | 维护深度 |
| `trust` | 业主对这个经纪人的信任 |
| `lastContactDay` | 最近联系时间 |
| `isPrimaryMaintainer` | 是否主维护人 |
| `ownerNeedUnderstanding` | 对业主诉求的理解程度 |

### BrokerCustomerRelation

这条关系回答：

> 这个经纪人和这个客户之间，现在维护得怎么样。

建议字段：

| 字段 | 含义 |
| ---- | ---- |
| `brokerId` | 哪个经纪人 |
| `customerId` | 哪个客户 |
| `maintenanceLevel` | 维护深度 |
| `trust` | 客户对这个经纪人的信任 |
| `lastContactDay` | 最近联系时间 |
| `isPrimaryMaintainer` | 是否主维护人 |
| `demandUnderstanding` | 对客户需求的理解程度 |
| `nextFollowUpIntent` | 下一次跟进意图 |
| `brokerKnownCustomerName` | 这个经纪人视角里记录的客户称呼 |
| `brokerKnownDemand` | 这个经纪人理解到的客户需求 |
| `visibilityToOtherBrokers` | 对其他经纪人是否可见，默认不可见 |

这两条关系会影响：

1. 客户是否愿意继续看你推荐的房。
2. 业主是否愿意听你的价格建议。
3. 线索是否适合转接给别人。
4. 商圈经理是否会介入协调。

### 一个客户可以有多个经纪人关系

现实里，一个客户经常会同时问多个经纪人。

所以模型上要允许：

```text
Customer 1 -- N BrokerCustomerRelation
Broker   1 -- N BrokerCustomerRelation
```

这代表：

- 同一个客户可以被多个经纪人维护
- 每个经纪人只知道自己那条关系
- 经纪人之间默认不知道彼此也在跟这个客户
- 平台后台可以知道这些关系可能指向同一个真实客户

### 平台后台客户识别

平台可以有一个后台能力：

`CustomerIdentityResolution`

它回答：

> 多个经纪人维护的客户记录，是否其实是同一个真实客户。

建议字段：

| 字段 | 含义 |
| ---- | ---- |
| `resolvedCustomerId` | 平台识别出的真实客户 id |
| `sourceRelationIds` | 哪些经纪人客户关系可能指向同一个人 |
| `confidence` | 识别置信度 |
| `dedupeStatus` | 未确认 / 可能重复 / 已确认 |
| `privacyLevel` | 识别结果对谁可见 |

注意：

- 这属于平台后台能力
- 不等于把客户明细公开给所有经纪人
- 前台可以提示“存在撞客风险”或“客户可能多方咨询”
- 但不能直接告诉经纪人“谁也在跟这个客户”，除非规则允许

### 对机会推进的影响

同一个真实客户找多个经纪人，会影响机会推进：

1. 客户对多套房的比较会更复杂。
2. 客户可能从一个经纪人那里看房，从另一个经纪人那里出价。
3. 客户注意力可能被多个经纪人分散。
4. 客源端归因会变复杂。
5. 如果跨品牌成交，可能形成丢客。

---

## 4.4 房源公开、客户私有、平台可算

这条是 ACN 里最容易混的业务边界。

### 房源公开

同一个 ACN 内，房源对经纪人公开。

意思是：

1. 同 ACN 经纪人可以看到房源基础信息。
2. 同 ACN 经纪人可以带自己的客户去看这套房。
3. 房源端经纪人仍然负责业主维护和房源质量。
4. 客源端经纪人负责自己的客户推进。

所以房源公开，不等于房源端价值消失。

### 客户私有

客户不是 ACN 公开池。

意思是：

1. 客户可以被多个经纪人同时维护。
2. 每个经纪人只看得见自己维护的那条客户关系。
3. 其他经纪人不能随便触达。
4. 客户是否转介，要通过规则或事项发生。

所以不能把客户建成 `AcnCustomerVisibility` 这种默认公开的概念。

更准确的是：

- `BrokerCustomerRelation`：谁维护这个客户
- `CustomerPrivacyScope`：谁可以看、谁可以触达、谁只能看到匿名统计
- `CustomerIdentityResolution`：平台后台识别多个客户关系是否指向同一个真实客户

### 平台可算

平台可以基于客户画像做全量计算。

这个“可算”和“可见”不是一回事。

平台可以做：

1. 拿所有客户画像和所有房源做匹配。
2. 给每套房算准客规模。
3. 给每套房算机会分。
4. 给经纪人提示“这套房在 ACN 内有多少潜在客户”。
5. 给商圈经理提示“哪些房有客户池，哪些房缺客户池”。

但平台不应该直接把别人的客户明细暴露出来。

### 平台全量匹配

本质上可以理解为：

```text
for each case in ACN.listings:
  for each customer in ACN.customers:
    score = match(customer.profile, case.profile, price, market)
    write PlatformCaseCustomerMatch(caseId, customerId, score)
```

这个结果用于生成：

| 输出 | 含义 |
| ---- | ---- |
| `potentialCustomerCount` | 这套房潜在适配客户数 |
| `highFitCustomerCount` | 高匹配客户数 |
| `reachableCustomerCount` | 可通过合规方式触达的客户数 |
| `caseOpportunityScore` | 房源机会分 |
| `anonymousCustomerSegments` | 匿名客户类型分布 |

注意：

- `customerId` 可以在后台存在
- 前台给非维护经纪人时，应只展示匿名统计
- 真要触达，需要发起转介、协作或商圈经理协调

### 机会分是什么

机会分不是成交概率。

它回答的是：

> 这套房在当前 ACN 客户池里，有多大客户基础。

建议输入：

1. 客户预算和价格是否匹配。
2. 客户板块偏好是否匹配。
3. 客户户型偏好是否匹配。
4. 客户需求标签是否匹配。
5. 客户活跃度是否足够。
6. 客户是否已经被强关系房源占住注意力。
7. 是否能合规触达。

所以：

- `caseOpportunityScore` 是房源级机会分
- `CustomerCaseRelation.fitScore` 是具体客户和具体房源的匹配分
- 真正推进阶段仍然要等客户进入关系后，再变成 `CustomerCaseRelation`

## 4.5 房源端和客源端

同一个 ACN 内的联卖，一定要分两端。

### 房源端

房源端负责：

1. 房源录入和维护。
2. 业主沟通和信任维护。
3. 价格反馈和调价沟通。
4. 房源质量、开放日、钥匙、照片、卖点等基础动作。

房源端的核心指标：

| 指标 | 含义 |
| ---- | ---- |
| `listingControl` | 对房源和业主的掌控力 |
| `ownerTrust` | 业主对房源端的信任 |
| `listingQuality` | 房源维护质量 |
| `listingExposureContribution` | 房源端带来的曝光贡献 |

### 客源端

客源端负责：

1. 获取客户。
2. 匹配房源。
3. 带看和复看。
4. 出价和成交推进。

客源端的核心指标：

| 指标 | 含义 |
| ---- | ---- |
| `customerControl` | 对客户的掌控力 |
| `customerTrust` | 客户对客源端的信任 |
| `showingQuality` | 带看和讲解质量 |
| `offerPushPower` | 推动出价的能力 |

### 一次联卖成交

一次 ACN 内成交，最少要记录：

| 字段 | 含义 |
| ---- | ---- |
| `caseId` | 哪套房 |
| `buyerCustomerId` | 哪个客户 |
| `listingSideBrokerId` | 房源端经纪人 |
| `customerSideBrokerId` | 客源端经纪人 |
| `listingSideStoreId` | 房源端门店 |
| `customerSideStoreId` | 客源端门店 |
| `brandId` | 所属品牌 |
| `acnId` | 所属 ACN |
| `commissionSplit` | 分佣结果 |
| `isYourListing` | 是不是玩家维护的房源 |
| `isYourCustomer` | 是不是玩家维护的客户 |

这会直接影响结果页、复盘页和排行榜。

## 5. 竞品要重新理解

以前说 `Rival`，容易理解成一个黑盒竞品力量。

但更准确的是：

> Rival 不是一个东西，而是一组来自不同品牌、不同门店、不同经纪人的竞争和合作力量。

所以后面建议：

1. 早期可以保留 `RivalPressure` 做简化。
2. 中期要把 `Rival` 拆成 `RivalBrand / RivalStore / RivalBroker`。
3. 同品牌同 ACN 内部首先是联卖关系，其次才有抢时机和分佣博弈。
4. 不同品牌之间，才是明确竞争关系。

### 不同品牌 = 竞争

如果客户被不同品牌成交：

- 你的客户被别的品牌成交，算丢客。
- 你的房源被别的品牌成交，算丢盘。
- 别的品牌拿走商圈内更多成交，会抬升它的市场占有率。

### 同品牌同 ACN = 联卖

如果同 ACN 内别人带客户成交了你的房源：

- 从品牌角度看，这是品牌内成交，不是品牌输给竞品。
- 从房源端角度看，你保住了房源成交价值。
- 从客源端角度看，对方拿到了客户推进价值。
- 从玩家体验看，要看你是否是房源端、客源端，还是两端都不是。

### 丢盘是什么

丢盘不是“这套房成交了但不是我签单”这么简单。

更准确的定义是：

> 你维护或主控的房源，被非你控制的一方成交，且你没有保住房源端价值。

丢盘可能有三种：

| 类型 | 解释 |
| ---- | ---- |
| 跨品牌丢盘 | 你的房源被其他品牌成交，最严重 |
| 同 ACN 弱丢盘 | 同 ACN 成交，但你房源端价值被弱化 |
| 内部抢成交 | 同 ACN 内别人抢了客源端结果，但房源端仍在你这 |

这三类要分开，不然后面复盘会非常混。

## 5.1 品牌市场占有率

品牌内要看市场占有率。

市场占有率不是一个装饰数字，它影响：

1. 客户天然信任。
2. 业主授权意愿。
3. ACN 房源流通效率。
4. 跨品牌竞争强度。
5. 品牌内门店目标压力。

### 建议字段

| 字段 | 含义 |
| ---- | ---- |
| `brandMarketShareByBizArea` | 品牌在商圈内成交占比 |
| `brandListingShareByBizArea` | 品牌在商圈内房源占比 |
| `brandCustomerShareByBizArea` | 品牌在商圈内客户触达占比 |
| `brandWinRateAgainstCompetitors` | 对其他品牌竞争胜率 |
| `brandLostListingCount` | 丢盘数量 |
| `brandLostCustomerCount` | 丢客数量 |

### 占有率怎么影响游戏

| 影响对象 | 影响方式 |
| -------- | -------- |
| 业主 | 占有率高，授权更容易；占有率下降，业主更容易动摇 |
| 客户 | 占有率高，客户更容易相信品牌推荐 |
| 房源 | 占有率高，曝光和联卖效率更强 |
| 竞品 | 对手占有率高，你的竞争压力更大 |
| 门店 | 占有率下滑，会带来目标压力和动作要求 |

## 6. ACN 对游戏里的关键影响

## 6.1 对房源

ACN 会影响：

1. 房源被多少经纪人看到。
2. 是否容易被同品牌门店共同推广。
3. 房源维护是否稳定。
4. 是否会出现内部重复触达业主。
5. 房源端和客源端是否能顺畅联卖。
6. 玩家维护的房源是否发生丢盘。

## 6.2 对客户

ACN 会影响：

1. 客户线索是否能被网络接住。
2. 客户是否被同品牌不同经纪人重复触达。
3. 客户在多套房之间的流转速度。
4. 客户是否被跨品牌竞品抢走。

## 6.3 对业主

ACN 会影响：

1. 业主是否相信“这个品牌能卖掉”。
2. 业主是否愿意接受开放日或联合推广。
3. 多个经纪人触达时，业主会不会觉得乱。
4. 内部协作好时，业主信任可能上升；协作差时，信任可能下降。

## 6.4 对玩家

ACN 会影响：

1. 玩家能借多少品牌和门店力量。
2. 玩家是不是必须自己完成所有动作。
3. 玩家是否可以发起协作事项。
4. 玩家是否会被同品牌同 ACN 的其他经纪人分走结果。
5. 玩家这次成交到底是房源端贡献、客源端贡献，还是两端都有。
6. 玩家是否丢盘、丢客，还是完成联卖。

---

## 7. 和现有模型的连接

## 7.1 和 MarketModel

市场模型回答外部环境。

组织层回答内部网络。

两者关系是：

- 市场热，品牌曝光会放大效果。
- 市场冷，ACN 协作能力能缓冲下滑。
- 商圈强，门店能力会更明显。

## 7.2 和 GoodHouseModel

好房分里的 D1、D3 会被 ACN 影响：

- D1：ACN 强，准客池更厚。
- D3：品牌强、协作好，业主更愿意配合。

D2 不应该被 ACN 直接改变。
房子本身还是房子本身。

## 7.3 和 PriceModel

品牌和 ACN 不直接决定市场估价。

但会影响：

1. 业主是否愿意相信市场反馈。
2. 调价 Matter 成功率。
3. 客户出价是否更有信心。

## 7.4 和 Matter

组织层会新增几类 Matter：

| Matter | 含义 |
| ------ | ---- |
| `acn_collaboration` | 发起同品牌协作 |
| `store_joint_push` | 门店联合推广 |
| `brand_owner_report` | 用品牌背书向业主汇报 |
| `lead_handoff` | 客户线索转接 |
| `conflict_resolution` | 撞客或撞盘冲突处理 |
| `co_sale_coordination` | 联卖协同 |
| `listing_side_defense` | 房源端保盘 |
| `customer_side_push` | 客源端推进 |
| `lost_listing_recovery` | 丢盘挽回 |

## 8. 日结里怎么计算

日结时组织层建议放在市场之后、客户业主之前。

顺序是：

1. 先算市场事件。
2. 再算品牌和 ACN 的组织动作。
3. 再算商圈经理动作。
4. 再算经纪人的维护池变化。
5. 再算房源、业主、客户和机会。

原因：

> 品牌和 ACN 是连接市场和个体的中间层。它先把市场信号转成组织动作，再影响具体房源和客户。

每天可能发生：

1. 品牌曝光上升或下降。
2. ACN 协作效率变化。
3. 门店联合推广启动。
4. 同品牌内部经纪人接力客户。
5. 内部竞争导致某条机会被分流。
6. 跨品牌竞品抢走客户注意力。
7. 同 ACN 内发生联卖成交。
8. 玩家房源被别人客源端成交。
9. 玩家房源被跨品牌成交，形成丢盘。
10. 品牌在某商圈市场占有率变化。
11. 商圈经理调整经纪人任务重点。
12. 商圈经理发起保盘或联卖协调。
13. 经纪人维护的业主池和客户池发生冷却或升温。

## 9. 最小实现建议

第一版不要一上来做很复杂。

建议先做 4 个字段：

1. `brandReputation`
2. `acnCollaborationPower`
3. `storeTrafficPower`
4. `internalCompetitionLevel`
5. `brandMarketShare`
6. `listingSideControl`
7. `customerSideControl`
8. `lostListingRisk`
9. `managerCoordinationPower`
10. `brokerOwnerMaintenanceLevel`
11. `brokerCustomerMaintenanceLevel`

第一版先让它们影响：

1. 房源曝光。
2. 客户进入率。
3. 业主信任变化。
4. 竞品拉扯。
5. 联卖成交归因。
6. 丢盘风险。
7. 线索分配。
8. 每日优先级。
9. 业主和客户维护关系冷却。

等系统稳定后，再把 ACN 拆成更细的合作规则和分佣规则。

## 10. 一句话收尾

经纪公司的本质不是“一个公司字段”，而是：

> 公司拥有品牌，品牌承载信任，品牌内部用 ACN 把门店、经纪人、房源和客户连接起来。

这层一旦建出来，竞品、合作、分佣、线索流转、品牌背书就都能进系统了。
