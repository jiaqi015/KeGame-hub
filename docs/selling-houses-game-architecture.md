# 我是王牌维护人 · 玩法架构草图

这份文档用于重构“我是王牌维护人”的核心玩法。目标不是继续给现有动作补数值，而是把玩法从“点技能”改成“处理事项”，让玩家真正扮演维护人，围绕房源、房东、客户、合作经纪人和商圈资源做周经营。

## 核心判断

当前版本的问题不在于某个动作数值偏弱，而在于基本单位选错了：

- 当前基本单位是“动作”
- 真实业务基本单位是“事项”
- 当前主循环是“每天花精力点按钮”
- 更合理的主循环应是“每周处理固定节奏和突发事项”

因此重构方向应是：

- 保留房源经营主题
- 降低“房东窗口倒计时”这类游戏化字段的重要性
- 提升固定例会、带看反馈、面访、开放日筹备和周反馈的权重
- 让每个动作都嵌入一个有来有回的交互模板

## 一句话玩法

玩家每周接手一组房源事项，在有限时间里决定先处理什么、怎么处理、向谁汇报、把哪些盘提报到聚焦会，并承担每次处理带来的后续连锁结果。

## 设计目标

- 让玩家像维护人，而不是像在放技能
- 让开放日成为周经营中的中枢事项，而不是普通按钮
- 让每个动作都有对象反馈、玩家应对、结果分叉和后续痕迹
- 让“建议执行”升级为“建议先处理哪个事项”
- 让系统易于继续扩展更多真实业务内容

## 核心循环

推荐采用“周经营 + 日事件”的双层循环。

### 周循环

1. 系统生成本周事项池
2. 玩家决定本周优先处理哪些事项
3. 日内推进事项，接收新的事件和反馈
4. 周末统一复盘，结算资源、关系和盘面变化
5. 进入下一周

### 日循环

1. 读取当天新增事项
2. 玩家选择处理顺序
3. 进入交互
4. 结算即时结果
5. 生成后续事项或风险

## 玩法对象

维护人不是只维护房东，而是在同时维护四类对象。

### 1. 房源

关注点：

- 当前价格是否有竞争力
- 卖点表达是否清晰
- 展示准备度是否足够
- 开放日是否值得做
- 当前盘面是热还是冷

### 2. 房东

关注点：

- 对维护人的信任
- 对市场反馈的接受程度
- 对价格调整的松动程度
- 情绪是否稳定
- 是否愿意继续投入配合

### 3. 客户与线索

关注点：

- 有效线索数量
- 线索来源结构
- 当前阶段分布
- 高意向客户数量
- 带看后真实顾虑

### 4. 组织资源

关注点：

- 商圈聚焦资源位
- 合作经纪人支持
- 开放日资源支持
- 个人在商圈内的话语权

## 状态架构

建议把当前散落在 `case` 上的状态拆成四层。

### ListingState

房源本身状态。

建议字段：

- `pricingPosition`
- `storyClarity`
- `displayReadiness`
- `listingHeat`
- `showingReadiness`
- `strategyTag`
- `focusEligible`

### SellerState

房东关系状态。

建议字段：

- `sellerTrust`
- `sellerConfidence`
- `sellerPatience`
- `priceFlexReadiness`
- `cooperationLevel`
- `emotionLevel`
- `communicationDebt`

说明：

- `sellerConfidence` 用来表达“房东对这条销售路径有没有信心”
- `sellerPatience` 不再每日机械递减，而是受到“连续无进展”和“反馈质量差”的影响
- `communicationDebt` 表示你欠房东多少解释和汇报

### DemandState

客户与漏斗状态。

建议字段：

- `activeLeadCount`
- `leadMix`
- `highIntentLeadCount`
- `shadowLeadCount`
- `stageDistribution`
- `recentShowingFeedback`
- `postOpenDayFollowups`

### OrgState

组织资源状态。

建议字段：

- `focusScore`
- `brokerSupport`
- `internalConfidence`
- `resourceSlots`
- `openDaySupport`
- `maintainerCredibility`

## 事项系统

事项应成为主玩法单位。

### 事项定义

每个事项建议包含：

- `id`
- `type`
- `source`
- `title`
- `summary`
- `caseId`
- `stakeholders`
- `priority`
- `deadline`
- `interactionTemplate`
- `contextPayload`
- `successEffects`
- `partialEffects`
- `failureEffects`
- `followupGenerators`

### source 分类

- `fixed`
  固定经营事项
- `event`
  事件驱动事项
- `chain`
  上一个事项结算后生成的连锁事项

### stakeholders 分类

- `seller`
- `buyer`
- `broker`
- `internal`
- `market`

## 事项池结构

推荐把事项分成三层。

### A. 固定事项

这些每周会稳定出现，是周节奏的骨架。

- `房源聚焦会提报`
- `每周业主反馈`
- `周末带看高峰排布`
- `开放日筹备复盘`
- `带看反馈整理`

### B. 事件事项

这些由盘面变化或市场触发。

- `竞品降价应对`
- `客户带看强反馈`
- `房东情绪波动`
- `合作经纪人回传情报`
- `报价桌进入冲刺`

### C. 连锁事项

这些是玩法节奏的真实来源。

- 开放日后生成 `追到访客`
- 提报失败后生成 `补证据再申请`
- 调价沟通后生成 `更新市场口径`
- 面访后生成 `房东补充要求`

## 周节奏引擎

推荐让系统每周固定生成一份经营节奏。

### 周一

- 汇总上周结果
- 处理高优先级带看反馈
- 准备本周提报素材

### 周二

- 商圈房源聚焦会
- 决定资源位和本周重点盘

### 周三

- 跟进客户
- 对线合作经纪人
- 修正卖点和邀约策略

### 周四

- 安排房东面访或重点沟通
- 为周末开放日或高峰带看做准备

### 周五

- 做每周房东反馈
- 锁定周末动作和价格口径

### 周末

- 开放日
- 集中带看
- 报价推进

说明：

- 周节奏不是硬脚本，而是高概率骨架
- 玩家每周都知道“哪些事大概率会来”
- 真正变化来自事件事项和连锁事项

## 四类交互模板

不是每个动作都做一套 UI，而是让事项复用少数几种交互模板。

### 1. 汇报型

适用事项：

- 房源聚焦会提报
- 每周业主反馈
- 开放日前沟通

结构：

1. 玩家先组织事实和主张
2. 对方提出质疑
3. 玩家做回应
4. 系统给出结论

影响：

- 房东信任
- 组织资源
- 后续事项优先级

### 2. 博弈型

适用事项：

- 调价沟通
- 面访
- 议价冲刺
- 经纪人对线

结构：

1. 对方先亮态度
2. 玩家选策略
3. 系统按上下文判定结果
4. 结果留下长期痕迹

影响：

- 价格空间
- 关系强度
- 合作度
- 成交机会

### 3. 诊断型

适用事项：

- 带看反馈整理
- 客户顾虑分析
- 竞品动作分析

结构：

1. 系统提供线索和碎片信息
2. 玩家判断问题根因
3. 玩家选择下一步动作方向
4. 结果影响后续事项质量

影响：

- 推荐事项是否准确
- 后续开放日准备质量
- 卖点和价格策略

### 4. 执行型

适用事项：

- 精修卖点
- 流量投放
- 开放日筹备与执行

结构：

1. 玩家先选执行方案
2. 系统给市场反馈
3. 系统转译成客户结果和房东感知
4. 自动生成后续事项

影响：

- 线索结构
- 盘面热度
- 房东信心
- 下周事项池

## 开放日的架构定位

开放日不应再是普通动作，而应是“周中型项目事项”。

### 开放日三段式

#### 1. 争取立项

来源：

- 房源聚焦会争取资源
- 房东面访争取同意

如果争取失败：

- 本周不能做开放日
- 生成 `补充依据` 或 `改成普通带看策略`

#### 2. 筹备

玩家决定：

- 主打卖点
- 邀约对象
- 价格口径
- 是否同步合作经纪人

筹备质量影响：

- 到访量
- 到访结构
- 客户是否够精准

#### 3. 执行与复盘

系统结算：

- 到访人数
- 到访质量
- 高意向客户数
- 房东对这次活动的主观感受

后续自动生成：

- `追高意向到访客`
- `向房东解释结果`
- `复盘卖点失焦`

## 结果与后遗症设计

每个事项都应同时产生两类结果。

### 即时结果

例如：

- 获得资源位
- 新增 2 个高意向客户
- 房东接受小幅调价
- 成交桌保住了

### 长期痕迹

例如：

- 房东开始接受市场口径
- 合作经纪人更愿意给线索
- 公司内部更愿意给你下一次聚焦机会
- 房东对“热闹但无报价”的耐受度下降

建议引入 `persistentFlags` 这类轻量状态，用于承接长期痕迹。

示例：

- `seller_accepts_market_feedback`
- `broker_trust_high`
- `open_day_failed_once`
- `needs_price_reposition`
- `focus_meeting_rejected_recently`

## 推荐系统重构

当前“建议执行”应升级为“建议先处理哪个事项”。

推荐输出建议字段：

- `recommendedMatterId`
- `reason`
- `riskIfIgnored`
- `expectedOutcome`

示例文案：

- 先处理 `周反馈`
  房东已经连续两周未收到有效解释，如果这次仍然只报流水账，合作度会下降。
- 先处理 `开放日后追客`
  本周到访中有两位高意向客户，再拖一天将明显降温。
- 先处理 `房源聚焦会提报`
  这套房本周最有机会拿到公司资源位。

## 旧动作到新事项的映射

现有动作不必完全删除，但要降级为事项中的应对选项。

| 旧动作 | 新定位 |
|---|---|
| `owner-call` | `每周业主反馈` / `房东情绪波动` / `面访前沟通` 的应对选项 |
| `story` | `精修卖点` 事项中的执行方案 |
| `price-talk` | `调价沟通` 事项中的博弈选项 |
| `promote` | `投放策略` 事项中的执行方案 |
| `open-day` | `开放日项目` 的执行阶段，而不是独立按钮 |
| `showing` | `带看安排与现场反馈` 事项中的执行结果 |
| `negotiate` | `报价桌冲刺` 事项中的博弈选项 |
| `agent-sync` | `经纪人对线` 事项中的博弈选项 |

## 模块建议

如果后续进入实现阶段，建议把结构拆成以下模块。

### 1. Week Rhythm Engine

职责：

- 生成固定事项
- 标注本周主题
- 控制例会和周末高峰

### 2. Matter Generator

职责：

- 根据盘面状态和事件生成事项
- 决定事项优先级和 deadline

### 3. Interaction Resolver

职责：

- 根据交互模板执行一次事项
- 结算即时结果和长期痕迹

### 4. Follow-up Generator

职责：

- 根据事项结果生成连锁事项

### 5. Recommendation Engine

职责：

- 从事项池中找出最值得先处理的事项
- 解释推荐原因

## 迭代顺序

推荐按以下顺序改，而不是一次性推翻全部实现。

### Phase 1

先引入“事项池”，但底层还可暂时复用现有动作数据。

目标：

- Dashboard 从显示 `priorities` 改成显示 `matters`
- 推荐系统先推荐事项

### Phase 2

把固定事项做出来。

优先做：

- `房源聚焦会提报`
- `每周业主反馈`
- `带看反馈整理`

### Phase 3

把开放日改造成三段式项目事项。

优先做：

- 争取立项
- 筹备
- 执行后追踪

### Phase 4

把旧动作全部降级成事项内选项，逐步移除“点技能”感。

## 最终体验判断标准

如果重构成功，玩家在玩的时候应该会自然说出这些话：

- “这周我得先准备聚焦会提报。”
- “开放日做不做，取决于这套盘现在值不值得押资源。”
- “房东不是单纯不耐烦，而是开始不信这条销售路径了。”
- “这次带看反馈说明不是继续拉流量，而是要先改卖点。”
- “我不是在点动作，我是在经营这套盘的一周。”

如果玩家还在说“我先点哪个按钮收益最高”，那就说明架构还没真正转过来。
