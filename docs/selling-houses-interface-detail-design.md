# 卖房（资产顾问）界面信息架构详细设计

最后更新：2026-04-19

这份文档是“界面信息架构”的详细设计版。

它回答：

> 玩家真正看到的界面是什么样；从一级入口到详情页怎么钻；哪些对象怎么展示；新闻、事件、事实、日志怎么组织；第一版应该先做哪些页面。

它不回答：

- 最终视觉风格
- 具体 CSS 布局
- 接口路径
- 数据库字段名

它只回答产品和架构层面的信息组织。

---

## 0. 总体结论

玩家玩的不是“后台系统”，而是一个经营工作台。

建议第一版界面长这样：

```text
┌──────────────────────────────────────────────────────────────┐
│ 顶部状态条：第几天 / 周几 / 剩余天数 / 精力 / 推广金 / 目标分 / Continue │
├──────────┬───────────────────────────────────────┬───────────┤
│ 左侧导航 │ 中间主工作区                            │ 右侧侧栏   │
│          │ 日历 / 列表 / 雷达 / 详情                │ 提醒/动作   │
│ 经营概览 │                                       │ 建议Matter │
│ 房源     │                                       │ 可做动作    │
│ 客户     │                                       │ 影响预估    │
│ 市场     │                                       │             │
│ 复盘     │                                       │             │
│ 结果     │                                       │             │
│ 我       │                                       │             │
├──────────┴───────────────────────────────────────┴───────────┤
│ 底部 / 抽屉：流水日志，全局 / 对象 / 日期三种视角              │
└──────────────────────────────────────────────────────────────┘
```

核心原则：

> 中间看局面，右侧做选择，详情解释为什么，流水追溯发生过什么。

## 1. 信息层级

信息层级固定成 5 层：

```text
L1 一级导航
  -> L2 页面视图
    -> L3 分区 / 列表
      -> L4 卡片 / 行
        -> Detail 详情页 / 详情抽屉
```

### 1.1 L1 一级导航

回答：

> 我在哪个经营场景？

固定入口：

- `经营概览`
- `房源`
- `客户`
- `市场`
- `复盘`
- `结果`
- `我`

`开局` 不放在局内主导航里。
局开始后，开局信息收进“本局信息”。

### 1.2 L2 页面视图

回答：

> 这个场景下，我现在要判断什么？

例如：

- 经营概览：本周日历 / 今日视图 / 昨日情报
- 房源：全部房源 / 核心盘 / 风险盘 / 价格卡住 / 客户池薄
- 客户：已见面机会 / 后段机会 / 快流失 / 高匹配 / 比较负荷高
- 市场：雷达 / 行情 / 竞对
- 复盘：按天 / 按房源 / 按 Matter / 关键转折
- 结果：单房结局 / 总分三维 / 关键成交与丢盘 / 排行榜入口
- 我：本职状态 / 关系网络 / 复盘入口 / 战绩

### 1.3 L3 分区 / 列表

回答：

> 我应该看哪一组对象？

它是定位层，不要写太多解释。

### 1.4 L4 卡片 / 行

回答：

> 这一条值不值得点进去？

卡片只放摘要。

### 1.5 Detail 详情

回答：

> 为什么是这样，我能做什么，证据在哪里？

详情才放完整解释、事实链、影响对象、推荐 Matter、流水日志。

## 2. 顶部状态条

顶部状态条是局内仪表，不是分析区。

### 显示内容

```text
第 12 天｜周四｜剩余 18 天｜精力 7/10｜推广金 4.2w｜标准局｜当前预估 66 / 目标 68
```

### 字段来源

| 显示 | 来源 |
| ---- | ---- |
| 第几天 / 周几 / 剩余天数 | `TimeContext` + `GameRun` |
| 精力 | `BrokerRuntimeState.energy` |
| 推广金 | `BrokerRuntimeState.marketingBudget` |
| 难度 | `DifficultyTier` |
| 当前预估 / 目标分 | `ResultProjection` + `RunDifficultyConfig` |

### 不放什么

- 不放复杂图表
- 不放全量提醒
- 不放事件列表

## 3. 右侧洞察与行动侧栏

右侧侧栏是全局复用组件。

它根据当前选中对象变化。

### 3.1 没有选中对象时

显示全局优先级：

```text
今日优先
1. A 房：价格窗口打开，适合谈价
2. B 房：客户二看后 2 天未跟进
3. 本周末：开放日窗口即将开启
```

### 3.2 选中房源时

显示房源相关动作：

```text
当前主矛盾：价格卡住

建议 Matter
- 定价沟通
- 二看客户反馈整理
- 同类竞品对比

可做动作
- 给业主做价格反馈
- 推动客户二看
- 申请周末开放日

不能做
- 直接推进出价：客户信心不足
```

### 3.3 选中客户 / 机会时

显示机会推进建议：

```text
当前阶段：看房后
推进风险：停滞 3 天

建议 Matter
- 二看邀约
- 竞品比较沟通
- 价格接受度确认
```

### 3.4 选中新闻 / 事件时

显示影响和下一步：

```text
影响范围：同商圈 80-100 平改善盘
影响房源：A 房、C 房
建议动作：给 A 房业主做竞品反馈
```

## 4. 底部流水日志

流水日志是系统信任感的底座。

玩家必须能追问：

> 为什么这个客户推进了？为什么这套房变差了？昨天到底发生了什么？

### 4.1 三种流水入口

1. 全局流水
   看整局发生过什么。
2. 对象流水
   看某套房、客户、机会、Matter、活动发生过什么。
3. 日期流水
   从周日历点开某一天，看当天发生过什么。

### 4.2 日志条目结构

```text
[第 12 天 周四] 客户李女士完成 A 房二看
来源：Matter「推动李女士二看」
影响：A 房机会阶段推进；客户信心 +；业主信心小幅回暖
相关：A 房 / 李女士 / 王业主
```

### 4.3 日志条目字段

```ts
type LogItemProjection = {
  id: string;
  happenedAtDay: number;
  title: string;
  summary: string;
  sourceType: 'player-action' | 'matter' | 'market' | 'system' | 'rival';
  severity?: 'info' | 'warning' | 'critical';
  relatedEntityRefs: EntityRef[];
  canOpenDetail: boolean;
};
```

### 4.4 过滤能力

必须支持：

- 全部
- 市场
- 房源
- 客户
- 业主
- Matter
- 竞品
- 风险
- 玩家动作

## 5. 经营概览详细设计

经营概览是默认入口。

它回答：

> 今天先处理谁。

这一页吸收 `Inbox`，但不把 Inbox 做成另一个世界。

更准确地说：

> 经营概览 = 一周经营日历 + 今日 Inbox + 昨日情报 + Continue 推进。

### 5.1 页面结构

```text
经营概览
  A. 顶部今日条
  B. 本周日历
  C. 今日 / 昨日新闻
  D. 必须回复
  E. 今日到达
  F. 今日日程
  G. 本周重点节点
```

建议布局：

```text
┌──────────────────────────────────────────────────┐
│  第 12 天｜周四｜09:00     [Continue ->]         │
│  当前预估 66 / 目标 68｜精力 7/10｜推广金 4.2w   │
├──────────────────────────────────────────────────┤
│  本周日历：周一 周二 周三 周四 周五 周六 周日     │
├──────────────────────────────────────────────────┤
│  今日 / 昨日新闻                                  │
│  · 同类盘昨晚新增 2 套降价                        │
│  · 周末开放日窗口即将开始                         │
├──────────────────────────────────────────────────┤
│  必须回复                                         │
│  [客户] 李女士：是否接受 940 万？ 剩 6h           │
│  [业主] 张先生第二次催促：有进展吗？ 剩 4h        │
├──────────────────────────────────────────────────┤
│  今日到达                                         │
│  · 新客户王先生，预算 800-900                     │
│  · 同 ACN 小王想联卖金桥名苑                      │
├──────────────────────────────────────────────────┤
│  今日日程                                         │
│  14:00 带看 @ 海悦名邸 9A                         │
│  16:30 业主面谈 @ 星辉海岸 12B                    │
└──────────────────────────────────────────────────┘
```

### 5.2 A. 本周日历

每一天显示三类东西：

- 新闻
- 事项
- 提醒

示例：

```text
周一
  新闻：朝阳东部同类盘降价
  事项：A 房业主反馈
  提醒：B 房客户 3 天未跟进

周六
  新闻：周末开放日窗口
  事项：C 房开放日
  提醒：高成本动作适合今天打
```

点击某一天，进入 `日期详情`。

### 5.3 日期详情

日期详情必须有。

结构：

```text
第 12 天 / 周四
  今日新闻
  完成事项
  机会变化
  业主变化
  价格变化
  风险提醒
  全部事件流水
```

### 5.4 今日摘要

一句话告诉玩家：

> 今天最重要的判断是什么。

例子：

```text
今天重点不是补流量，而是处理 A 房价格窗口和 B 房客户停滞。
```

### 5.5 昨日情报

昨日情报不是普通新闻。

它是日结后系统告诉玩家：

> 昨天有哪些变化会影响今天。

每条昨日情报都必须能点开新闻详情。

### 5.6 必须回复

必须回复只放强时效事项。

不是所有 Matter 都能进入这里。

进入条件：

- `priority = must_respond`
- 有明确截止时间
- 不处理会触发后果
- 和当前局面关键对象有关

典型来源：

- 客户还价
- 业主连续催促
- 开放日前确认
- 关键客户是否复看
- 联卖协商到期

卡片字段：

| 字段 | 含义 |
| ---- | ---- |
| 类型 | 客户 / 业主 / 房源 / 组织 |
| 标题 | 玩家要处理什么 |
| 关联对象 | 哪套房、哪个客户、哪个业主 |
| 剩余时间 | 还有多久必须处理 |
| 快捷动作 | 2-4 个高频动作 |
| 风险标识 | 逾期后果或关系风险 |

示例：

```text
[客户] 李女士：是否接受 940 万？
星辉海岸 12B · 第 3 次还价 · 剩 6h
[接受] [还价] [拒绝] [问业主]
```

### 5.7 今日到达

今日到达放今天新出现但不一定强阻塞的事项和事件。

包括：

- 新客户
- 新市场新闻
- 竞品动作
- 同 ACN 联卖邀约
- 系统推荐 Matter
- 日结后新增提醒

排序规则：

- 按发生时间倒序
- 关键风险可以置顶
- 不要和必须回复混在一起

### 5.8 今日日程

日程只放已经有明确时间槽的 Matter。

进入条件：

- `interactionTemplate = schedule`
- 或者 `scheduledSlot.day = today`

排序规则：

- 按时间正序

典型内容：

- 带看
- 业主面谈
- 开放日准备会
- 客户复看

### 5.9 Continue 按钮

Continue 不是简单“下一天”。

它应该推进到下一个需要玩家做决定的节点。

优先级：

1. 下一个必须回复到期点
2. 下一个日程 Matter
3. 下一个剧情 / 市场事件节点
4. 都没有，则推进到明早 9:00

状态规则：

| 状况 | Continue 状态 | 点击行为 |
| ---- | ---- | ---- |
| 有未处理必须回复，未到时效 | 灰态 | 提示先处理 |
| 有未处理必须回复，已过时效 | 可点 | 触发逾期后果后推进 |
| 没有必须回复 | 可点 | 推进到下一决策节点 |

伪代码：

```text
advanceUntilNextDecision()
  candidates = [
    nextMustRespondDeadline,
    nextScheduledMatterTime,
    nextStoryOrMarketNode,
    tomorrowMorning
  ]
  target = earliest(candidates)
  runTickUntil(target)
```

### 5.10 长跳暂不做成主能力

类似 `Go on Holiday` 的长跳能力，第一阶段不要放主路径。

原因：

- 会跳过大量必须回复
- 会批量触发客户、业主、开放日后果
- 对日结引擎和复盘要求很高

可以后置成高级能力。

## 6. 房源页详细设计

房源页是主战场。

它回答：

> 这套房怎么打。

### 6.1 页面结构

```text
房源页
  L2 视图切换
    全部 / 核心盘 / 风险盘 / 客户池薄 / 价格卡住

  L3 房源网格
    2 列房源卡片

  Detail 房源详情
    上段：房源与业主总览
    中段：事项区
    下段：机会区
    二级页签：业主与价格 / 客户机会 / 竞争与联卖 / 流水与成交
```

### 6.2 房源卡片

默认使用 2 列卡片网格。

原因：

- 当前局内房源规模是 6-8 套
- 玩家需要直观看到每套房的经营状态
- 列表更适合 30+ 房源的后台场景，不适合这个局内规模

卡片只放 7 类摘要：

1. 房源简称
2. 挂盘天数
3. 带看次数
4. 好房分
5. 热度 3 档
6. 状态标签，最多 2 个
7. 右上 Matter 未处理数

```text
┌──────────────┐
│ 星辉海岸 12B  │ ·3
│ 挂 28 天      │
│ 带看 5        │
│ 好房 82       │
│ 热度 ▲▲▲      │
│ 核心 · 在谈   │
└──────────────┘
```

卡片点击进入房源详情。

### 6.3 房源详情

房源详情建议是主详情页，不建议只做小抽屉。

整体采用三段式：

```text
┌─ 星辉海岸 12B ─────────────────────────┐
│ 上段：房源与业主总览                    │
│ 业主：李女士｜信任 58｜耐心 41          │
│ 138 平｜3 室｜挂牌 980 万｜心理 940 万  │
│ 好房 82｜热度 ▲▲▲｜挂盘 28 天｜带看 5   │
│ [调价] [约开放日] [诊断] [汇报业主]     │
├────────────────────────────────────────┤
│ 中段：事项                              │
│ [谈价] 李女士 940 答复 · 剩 6h          │
│ [带看] 林先生 14:00                     │
│ [诊断] 连续 2 次无出价，建议排查         │
│ [+ 新事项]                              │
├────────────────────────────────────────┤
│ 下段：机会                              │
│ 林先生｜二次带看｜热 ▲▲▲                │
│ 陈女士｜约面访｜热 ▲▲                   │
│ 王先生｜首次电话｜热 ▲                  │
└────────────────────────────────────────┘
```

三段职责：

- 上段
  查询层，像桌面参考资料，随时告诉玩家这套房的基本盘和业主状态。
- 中段
  主战场，承载当前这套房要推进的 Matter。
- 下段
  多客户并行，展示这套房上的已见面实名机会。

#### 总览

显示：

- 房源基础信息
- 当前热度 / 曝光 / 竞争压力
- 好房分 D1/D2/D3
- 当前主矛盾
- 本周建议打法

#### 业主

显示：

- 出售动机
- 性格
- 当前焦虑
- 信任
- 耐心
- 价格松动 readiness
- 最近沟通流水

#### 客户池

显示：

- 未见面潜力池
- 已见面实名机会
- 后段机会数
- 看房后机会数
- 快流失机会
- 下一步转化建议

这里必须分清：

- 未见面潜力池，只展示预估人群体量、主力画像、预算匹配和主要阻塞。
- 已见面实名机会，才进入详细阶段管理。
- 只有点击已见面机会，才进入机会详情。

潜力池示例：

```text
潜力池
预估潜在人群：160
高匹配人群：28
本周新增潜力：12
主力画像：刚需两房 / 预算 650-750
主要阻塞：价格略高、卖点不够清晰
建议：先精修卖点，再做定向推广
```

已见面机会示例：

```text
李女士｜看房后
信心：中上
风险：3 天未跟进
下一步：二看邀约
```

#### 价格

显示：

- 挂牌价
- 市场估价
- 业主心理价
- 价格差距
- 成交可行度
- 谈价窗口

#### Matter

显示：

- 进行中 Matter
- 建议 Matter
- 已完成 Matter
- 失败 Matter

点击 Matter，进入 Matter 详情。

#### 时间线

显示对象流水：

- 房源事件
- 业主事件
- 客户机会事件
- 价格事件
- 竞品事件

### 6.4 房源详情二级页签

房源详情除了三段式主视图，还需要四个二级页签。

#### 业主与价格

回答：

- 业主为什么卖
- 现在愿不愿意配合
- 价格是不是已经卡住
- 能不能谈价

包含：

- `OwnerProfile`
- `OwnerRuntimeState`
- `OwnerCaseRelation`
- `BrokerOwnerRelation`
- `PriceModelOutput`

#### 客户机会

回答：

- 这套房现在有哪些真实机会
- 哪些是后段机会
- 哪些快流失
- 潜力池够不够

包含：

- 未见面潜力池聚合
- 已见面实名机会
- `CustomerCaseRelation[]`
- 下一步 Matter

#### 竞争与联卖

回答：

- 谁在和这套房抢同一批客户
- 哪些相似房压力最大
- 同 ACN 有没有可借力机会
- 跨品牌有没有丢盘风险

包含：

- 竞品房源
- 相似度
- 客群重合度
- `CoSaleRelation`
- 品牌 / 门店压力

#### 流水与成交

回答：

- 这套房发生过什么
- 有没有成交记录
- 如果成交，是谁和谁成交
- 如果丢盘，丢在哪里

包含：

- 房源事件流水
- 相关 Matter
- `ClosedDealRecord`
- `CaseEndingProjection`

## 7. 客户页详细设计

客户页不是 CRM，也不是平台潜客池。

它回答：

> 哪些已经形成真实关系的客户机会值得推进。

没见过面的潜在人群，留在房源详情的潜力池里，只做规模和画像预估。

见过面的客户，才进入客户页和机会详情。

客户页的定位要再说清楚：

> 它是跨房源视角，不是主战场。

大多数时候，玩家会在房源详情下段处理机会。

客户页主要用来解决：

- 一个客户同时在看哪些房
- 这个客户是不是比较负荷过高
- 该推他看 A 房，还是先放 B 房
- 这个客户是否正在被竞品拉走

### 7.1 页面结构

```text
客户页
  L2 视图切换
    已见面机会 / 后段机会 / 快流失 / 高匹配 / 比较负荷高

  L3 客户机会列表
    客户行 / 机会卡片

  Detail 客户详情 / 机会详情
```

### 7.1.1 客户行

客户行不是联系人列表。

它要展示这个客户当前在局内的比较状态：

```text
林先生｜预算 600-700｜看过 3 套｜比较负荷 高
  星辉海岸 12B｜意向 ▲▲▲｜阶段 二看后
  海悦名邸 9A｜意向 ▲｜阶段 首次看房后
```

点击客户行进入客户详情。

点击某套房机会进入机会详情。

### 7.2 机会卡片

```text
李女士 -> A 房
阶段：看房后
匹配：高
信心：中上
风险：3 天未跟进
建议：二看邀约
```

### 7.3 客户详情

客户详情显示：

- 客户画像
- 当前状态
- 你和他的关系
- 他正在比较哪些房
- 推荐优先推进哪套
- 最近流水

结构建议：

```text
客户详情
  A. 基本画像
  B. 当前状态
  C. 正在比较的房
  D. 沟通与带看流水
  E. 下一步 Matter
```

这里不要放成传统 CRM：

- 不主打手机号
- 不主打联系人字段
- 不主打销售漏斗

重点是：

> 这个客户为什么在这些房之间摇摆。

### 7.4 机会详情

机会详情必须有。

显示：

- 当前阶段
- 阶段来源
- fitScore
- affordabilityScore
- intent
- confidence
- stagnationDays
- rivalPullScore
- 下一步 Matter
- 阶段流水

机会详情要明确一件事：

> 机会是 `客户 + 房源` 的关系，不是客户本人。

所以机会详情里必须同时能跳回：

- 客户详情
- 房源详情
- 相关 Matter
- 相关事件流水

## 8. 市场详细设计

市场回答：

> 外部环境哪里变了，对我有什么影响。

市场采用三子 tab：

1. `雷达`
2. `行情`
3. `竞对`

这三个词分别对应真实经营里的三类判断：

- 新情况
- 行情数据
- 同行动作

### 8.1 页面结构

```text
市场
  Tab A. 雷达
    昨日市场情报
    今日新情况
    受影响房源

  Tab B. 行情
    区域均价
    成交量
    供需比
    挂牌天数中位
    时间切换：本周 / 本月 / 本季

  Tab C. 竞对
    品牌 / 门店动态
    同类竞品房源
    成交榜
    联卖机会
    撬盘 / 丢盘风险
```

### 8.2 Tab A：雷达

雷达看事件流。

它回答：

- 今天有什么新情况
- 哪些市场事件会影响我手上的盘
- 哪些新闻应该转化成 Matter

每条新闻卡片：

```text
同类盘开始集中降价
范围：前滩商圈 / 80-100 平改善
影响：A 房、C 房
建议：给业主做竞品反馈
```

点击进入新闻详情。

### 8.3 新闻详情

新闻详情显示：

- 新闻标题
- 摘要
- 影响范围
- 底层事件列表
- 受影响房源
- 受影响客户 / 业主类型
- 建议 Matter

### 8.4 Tab B：行情

行情看数据面。

它回答：

- 现在价格水平怎么变
- 成交量是不是变了
- 供需比是不是恶化
- 挂牌天数是不是拉长
- 这套房所在板块是顺风还是逆风

建议至少显示：

| 模块 | 内容 |
| ---- | ---- |
| 区域均价 | 城市 / 区域 / 商圈均价走势 |
| 成交量 | 周 / 月 / 季成交量 |
| 供需比 | 新增客户与新增房源关系 |
| 挂牌天数中位 | 判断去化速度 |
| Segment 切换 | 总价带 / 户型段 / 客群段 |

行情页的图表可以简单，但口径必须稳定。

所有图表都必须能点到市场范围详情。

### 8.5 Tab C：竞对

竞对看同行动作。

它回答：

- 哪个品牌最近成交多
- 哪个门店在抢这类盘
- 哪些竞品房源正在和我抢同一批客户
- 同 ACN 有没有联卖机会
- 有没有丢盘、丢客风险

建议显示：

- 品牌成交榜
- 门店活跃榜
- 同类竞品房源
- 新挂盘 / 降价 / 成交
- 联卖邀约
- 撬盘风险

竞对详情第一阶段做到门店级即可。

具体到单个同行经纪人，可以作为后续增强，不要第一阶段就做太深。

### 8.6 层级下钻

层级：

```text
城市
  -> 区域
    -> 商圈
      -> 小区群
        -> segment
```

每一层都可以点开范围详情。

### 8.7 市场范围详情

显示：

- 当前热度
- 供给压力
- 竞品活跃
- 成交速度
- 最近新闻
- 受影响房源
- 竞品动静
- 联卖机会

## 9. Matter 详情设计

Matter 是玩法单位，所以必须能点开。

但 Matter 不应该都点进同一种页面。

建议固定三层：

1. 普通卡片
2. 独立页面
3. 专屏

---

### 9.0 Matter 的展示分层

#### A. 普通卡片

适合：

- 简短回复
- 单步确认
- 时效提醒
- 轻量沟通

展示位置：

- `经营概览 > 必须回复`
- `经营概览 > 今日到达`
- 房源详情中段
- 客户详情侧栏

打开方式：

- 抽屉
- 小弹层

典型场景：

- `client_call`
- 简单版 `report_to_owner`
- 带看前确认
- 开放日前确认

#### B. 独立页面

适合：

- 需要完整事实包
- 需要看参与对象
- 需要看已做动作和后续动作
- 需要反复回来推进

展示位置：

- 从房源详情中段进入
- 从客户详情进入
- 从复盘或日志回跳进入

典型场景：

- `showing`
- `valuation`
- `listing_prep`
- `negotiation`
- `report_to_owner`
- `diagnose`
- `co_selling`
- `closing_prep`

#### C. 专屏

适合：

- 有执行时段
- 有实时事件流
- 有多人和多对象同时变化
- 结束后要统一结算

第一阶段明确一类：

- `open_house`

以后如果还有别的 Matter 想做专屏，必须先满足这 4 条，不然不要轻易做。

### 9.1 Matter 卡片

```text
Matter：A 房定价沟通
阶段：prepare-evidence
对象：王业主 / A 房
截止：第 13 天
风险：业主防御较强
```

### 9.2 Matter 详情

结构：

```text
Matter 详情
  标题区
  当前阶段
  参与对象
  事实包
  已做动作
  下一步动作
  完成条件
  风险
  事件流水
```

Matter 详情必须能直接做动作或推进阶段。

### 9.3 Matter 页面与专屏的边界

不要把所有复杂事项都做成专屏。

更稳的规则是：

- 独立页面
  重点解决“判断和推进”
- 专屏
  重点解决“执行和实时承接”

例如：

### `negotiation`

适合独立页面，不适合专屏。

因为它核心是：

- 看事实
- 试探立场
- 推进条件

而不是持续实时操作。

### `showing`

默认做独立页面。

原因：

- 前面有预约
- 中间有现场执行
- 后面有反馈

但它的实时密度一般没有开放日那么高，不必第一阶段就做专屏。

### `open_house`

必须做专屏。

因为它有：

- 准备阶段
- 当天执行阶段
- 多客户并发
- 实时事件
- 统一结算

### `closing_prep`

只做独立页面。

因为合同、条件确认、过户准备，本质是流程页，不是实时操作页。

### 9.4 推荐的 Scene × 展示层级表

| Scene | 默认层级 | 打开方式 | 备注 |
| ---- | ---- | ---- | ---- |
| `client_call` | 普通卡片 | 抽屉 / 弹层 | 高频轻交互 |
| `report_to_owner` | 独立页面 | 页面 | 需要事实包 |
| `negotiation` | 独立页面 | 页面 | 需要上下文和多步博弈 |
| `valuation` | 独立页面 | 页面 | 本质是分析页 |
| `listing_prep` | 独立页面 | 页面 | 清单型推进 |
| `showing` | 独立页面 | 页面 | 预约 + 执行 + 反馈 |
| `diagnose` | 独立页面 | 页面 | 反复回看 |
| `co_selling` | 独立页面 | 页面 | 多方协作和归因 |
| `closing_prep` | 独立页面 | 页面 | 不等于成交落账 |
| `open_house` | 专屏 | 全屏工作台 | 独立执行与结算 |

### 9.5 升级规则

同一个 Scene 不是永远只能一种形态。

可以升级：

- `client_call`
  从普通卡片升级成独立页面
  条件：涉及多房比较、价格试探、家庭意见
- `co_selling`
  从轻量卡片升级成独立页面
  条件：涉及分工、分佣、房源端 / 客源端归因
- `showing`
  先从卡片预约发起，再进入独立页面执行

但：

> 第一阶段不要做“自动升专屏”，先把卡片和独立页面稳住。

## 11.5 开放日专屏详细设计

开放日是第一阶段唯一明确要做专屏的 Matter。

它不是普通活动详情。

原因：

- 有准备阶段
- 有当天实时执行
- 有多客户并发
- 会影响业主、客户、机会、竞品
- 结束后要统一结算

### 11.5.1 时间线

```text
T-72h
  必须回复：是否确认开放日

T-24h
  准备清单：业主是否到场、客户 RSVP、卖点材料

T-0
  切入开放日专屏

T+24h
  统一结算：客户机会、业主情绪、后续 Matter、竞品事件
```

### 11.5.2 专屏结构

```text
┌─ 开放日 · 金桥名苑 3F · 14:00-17:00 ──────┐
│  业主：李女士｜情绪：焦虑｜信任 58         │
├──────────────────────────────────────────┤
│  客户动线                 实时信号         │
│  14:12 王先生到场         王先生拍照        │
│  14:14 周女士到场         周女士询价        │
│  14:18 同行出现           张先生提前离场    │
├──────────────────────────────────────────┤
│  你的动作                                  │
│  [主动介绍采光] [回答价格问题]             │
│  [单拉客户到阳台] [稳住业主情绪]           │
│  [暗示价格弹性] [坚持当前报价]             │
├──────────────────────────────────────────┤
│  实时事件流                                │
│  · 14:20 你主动介绍采光，王先生点头         │
│  · 14:22 业主脱口说“价格可以再聊”           │
│  · 14:25 周女士询问学区                    │
└──────────────────────────────────────────┘
```

### 11.5.3 专屏内对象

必须显示：

- 房源
- 业主状态
- 到场客户
- RSVP 客户
- 同行 / 联卖参与
- 实时信号
- 玩家可选动作
- 事件流

### 11.5.4 专屏结束后的结算

开放日结束后必须生成：

- 到场客户结果
- 每个客户的 `CustomerCaseRelation` 变化
- 业主情绪和信任变化
- 竞品 / 同行事件
- 后续 `client_call` Matter
- 后续 `report_to_owner` Matter

也就是说：

> 开放日专屏结束，不是只写一句“开放日完成”，而是批量更新一组关系和后续事项。

## 13. 结果详细设计

结果页回答：

> 这一局打得怎么样。

排行榜回答：

> 放到长期和别人比较，处在什么位置。

### 13.1 结果页

显示：

- 单房结局
- 总分
- 三维得分
- 关键成交与丢盘
- 本局摘要
- 个人纪录变化
- 榜单变化

展示顺序建议固定：

1. 单房结局卡
2. 总分与三维
3. 关键成交与丢盘
4. 本局摘要
5. 排行榜入口

原因：

> 玩家最关心的是“这一单做成什么样”，不是先看一个抽象总分。

### 13.1.1 单房结局卡

每套房一张结局卡。

卡片显示：

- 房源名
- 结局类型
- 是否成交
- 是否守盘
- 业主满意度
- 关键转折
- 相关成交记录

结局类型来自 8 类 ending。

成交信息来自 `ClosedDealRecord`，不能从机会阶段倒推。

### 13.1.2 总分与三维

总分仍然保留。

但它主要用于：

- 段位
- 解锁
- 排行榜
- 跨局比较

页面表达上，单房结局是主角，总分是总结。

### 13.1.3 关键成交与丢盘

显示：

- 自成交
- 同 ACN 联卖成交
- 跨品牌丢盘
- 丢客
- 核心盘是否守住

所有内容都消费：

- `ClosedDealRecord[]`
- `DealStatsProjection`
- `RunResult`

### 13.2 排行榜页

三张榜：

- 总分榜
- 单局最高榜
- 局数榜

每行只显示：

- 排名
- 昵称
- 数字

点击自己或别人，可以看公开成绩摘要。

公开成绩摘要只展示：

- 昵称
- 总分
- 难度
- 单房结局摘要
- 成交 / 丢盘统计

不展示完整局内流水和客户明细。

## 14. 我页详细设计

`我` 页回答：

> 作为这个经纪人，我当前状态如何，关系网络如何，历史战绩如何。

它不是主战场。

它是玩家自身沉淀和回看的地方。

### 14.1 页面结构

```text
我
  A. 本职状态
  B. 关系网络
  C. 复盘入口
  D. 战绩
```

### 14.2 A. 本职状态

显示：

- 精力
- 声誉
- 当前压力
- 轻量技能标签

技能第一阶段只做展示或轻度修正，不做重 RPG。

原因：

- 游戏核心是房源经营
- 技能系统太早做深，会把主体验带偏

### 14.3 B. 关系网络

显示：

- 业主关系
- 客户关系
- 同行 / 联卖关系
- 组织关系

每条关系显示：

- 对象名
- 关系值
- 趋势
- 最近一次关键事件

点击可以进入对应详情或流水。

### 14.4 C. 复盘入口

显示：

- 本周
- 本月
- 本季
- 本年

第一阶段可以只支持本局内的本周 / 本月。

### 14.5 D. 战绩

显示：

- 当前局表现
- 历史最好
- 总局数
- 段位
- 单房结局卡汇总

这里可以复用结果页的结局卡组件。
