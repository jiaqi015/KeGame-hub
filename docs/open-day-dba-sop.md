# 开放日模块 DBA 工作 SOP

最后整理：2026-04-17

这份文档从 DBA 视角回答两个核心问题：

1. 代码和业务一直在变，数据库如何稳定适应，而不是被动追着改。
2. 日常该按什么流程工作，才能让 schema、持久化语义、迁移、回滚和审计都可控。

适用范围：

- `modules/open-day`
- `api/open-day-*`
- `server.ts` 中开放日相关接口
- Neon / 本地 file fallback / Blob 上传归档

## 一句话定位

在这个项目里，DBA 不是“表结构管理员”，而是“业务事实建模 + 数据生命周期守门人”。

要适应变化，核心不是追着字段跑，而是先守住这 4 件事：

1. 什么是稳定实体。
2. 什么是一次业务事件。
3. 什么数据该版本化。
4. 什么数据只是缓存，不算事实。

## DBA 的工作目标

每次面对需求变化，都优先保证：

- 业务事实不丢
- 历史可追溯
- 旧接口尽量兼容
- 迁移可灰度
- 回滚有路径
- 查询成本可预期

## 先分清 4 类数据

### 1. 业务事实

这类必须持久化，而且要尽量结构化。

例如：

- 上传了什么文件
- 解析出了什么数据集
- 用户保存了哪个方案
- 用户什么时候发起了一次测算
- 这次测算产出了哪些结果

### 2. 派生快照

这类通常也要持久化，但要明确它是“某个时点的结果”，不是原始事实。

例如：

- 某次分析结果行
- 某次方案版本快照
- 某次质量报告

### 3. 缓存

这类只负责加速，不负责表达业务事实。

例如：

- `cache_key -> analysis_result`
- `checksum + requestedSheet -> parse payload`

规则：

- 缓存可以丢
- 缓存命中不能替代业务事件入库
- 缓存表和业务表不要混语义

### 4. 会话 UI 状态

这类一般不应该进业务数据库，最多放本地浏览器状态。

例如：

- `isLibraryOpen`
- `isSidebarCollapsed`
- `searchTerm`
- `activeRow`
- `statusMessage`

## DBA 适应业务变化的基本原则

### 原则 1：先找稳定对象，不先加字段

收到需求时先问：

- 这是新实体，还是旧实体的新属性？
- 这是一次事件，还是一个长期对象？
- 这是当前状态，还是历史版本？

如果这些没分清，直接改表，后面通常会返工。

### 原则 2：优先追加，不轻易改写历史

业务在演进时，最容易犯的错是把“更新”做成“覆盖”。

开放日这类分析型业务更适合：

- 方案用 `template + version`
- 分析用 `run + result rows`
- 上传用 `artifact + dataset`

也就是：

- 当前态可以更新
- 历史态尽量追加

### 原则 3：把“业务动作”和“计算结果”分开

一次用户点击“开始测算”，是业务动作。

这次动作命中了缓存，还是实际重新算出来，是执行细节。

所以：

- `analysis_run` 记录动作
- `cache_hit` 只是属性
- `analysis_result` 记录结果

不能因为命中缓存，就不记录这次动作。

### 原则 4：兼容代码变化时，以数据契约为中心

代码模块会重构，组件会拆分，接口名字也可能换。

数据库适应变化时，优先围绕这些稳定契约：

- 实体 ID
- 外键关系
- 时间语义
- 版本语义
- 幂等键 / 指纹

不要把表设计绑死在某一个前端页面或某一个 service 方法上。

## DBA 适应代码变化的基本原则

### 原则 1：接口 DTO 不等于库表结构

当前仓库里有一些类型同时承担：

- 领域模型
- API DTO
- 持久化记录

从 DBA 视角，这种做法短期方便，长期会让 schema 被前端状态牵着走。

SOP：

- API 需要什么，不等于表里存什么
- 表里稳定字段优先
- JSON 列只用来兜底，不要偷懒把所有东西都塞进去

### 原则 2：运行时建表只适合早期

当前 `neonOpenDayDatabase.ts` 里的 `ensureSchema` 很适合快速迭代，但不适合长期治理。

SOP：

- 早期：允许 runtime ensure
- 中期：引入显式 migration
- 后期：schema 变更必须走 migration review

### 原则 3：本地 fallback 不是正式真相源

本地 file repo 的目标是开发可跑，不是正式持久化标准。

SOP：

- 业务语义以 Neon 版 schema 为准
- file fallback 只保证最小功能一致
- 不以本地 index 的临时行为反推正式库设计

## 日常工作 SOP

## SOP 0：接需求时先做变更分型

每个需求先归类到下面 5 类之一：

1. 新对象
   例如新增“数据集”概念。
2. 新事件
   例如新增“批量重算任务”。
3. 新版本维度
   例如方案要支持版本历史。
4. 新关系
   例如测算要关联上传文件、方案版本。
5. 新查询视角
   例如按方案聚合历史、按月份对比冠军盘。

输出物：

- 是否需要新表
- 是否需要新索引
- 是否需要迁移旧数据
- 是否需要兼容旧接口

## SOP 1：做数据影响评估

每次改 schema 前都要过一遍这 8 个问题：

1. 这次变化是新增还是修改？
2. 会不会影响历史回放？
3. 会不会让旧数据失真？
4. 是否需要版本化而不是覆盖？
5. 有没有幂等键或指纹？
6. 查询会按什么维度筛选？
7. 删除时是否需要级联？
8. 回滚时旧代码还能读吗？

输出模板：

- 变更对象：
- 新增字段 / 新增表：
- 兼容策略：
- 数据回填需求：
- 风险点：
- 回滚方式：

## SOP 2：决定“结构化列”还是 “JSON 列”

判断规则：

满足以下任意 1 条，就优先结构化：

- 要筛选
- 要排序
- 要 join
- 要聚合
- 要做唯一约束
- 要做外键
- 要作为业务身份

只有在这些场景下才优先 JSON：

- 短期兼容旧请求体
- 调试审计原始 payload
- 不稳定、暂未定型的附加信息

建议比例：

- 核心身份字段结构化
- 常用查询字段结构化
- 原始上下文可附带 JSON

## SOP 3：设计主键、外键和版本语义

### 主键

要求：

- 稳定
- 不依赖展示名
- 不把时间戳直接混成对象身份，除非它本身就是事件

规则：

- 对象型实体：稳定 id
- 事件型实体：独立 event/run id
- 版本型实体：`parent_id + version_no`

### 外键

要求：

- 能建外键就尽量建
- 不能建外键时，也至少保证语义上一致的引用字段

最低要求：

- `analysis_run.source_upload_id -> upload_artifact.id`
- `analysis_run.dataset_id -> dataset.id`
- `analysis_run.scenario_template_version_id -> scenario_template_version.id`

### 版本

遇到这些词，优先考虑版本表：

- 更新方案
- 回滚
- 草稿 / 发布
- 对比前后差异

## SOP 4：设计迁移路径

变更上线前必须写清楚迁移策略。

优先采用这三种方式之一：

### 方式 A：加表不改旧表

适合：

- 新功能
- 低风险扩展

步骤：

1. 新增表
2. 新代码双写或只写新表
3. 读路径灰度切换
4. 稳定后再收缩旧逻辑

### 方式 B：给旧表加列

适合：

- 小范围补信息
- 暂时不想大迁移

步骤：

1. 先加 nullable 列
2. 新代码开始写
3. 回填旧数据
4. 验证完成后再考虑 NOT NULL 或索引

### 方式 C：拆表 + 双写

适合：

- 历史快照要升级成 run/result model
- 模板表要升级成 template/version model

步骤：

1. 新增目标表
2. 写路径双写
3. 后台回填
4. 读路径切换
5. 停止旧表写入
6. 旧表保留观察期

## SOP 5：上线前检查

每次上线前至少检查：

- migration 是否幂等
- 新索引是否会锁太久
- 旧代码能否容忍新增列
- 旧数据是否会读崩
- 回放链路是否还能恢复老记录
- 本地 fallback 是否仍能跑

如果涉及历史表，还要额外检查：

- 分页是否稳定
- 排序字段是否有索引
- 最近 8 条和全量查询语义是否一致

## SOP 6：上线后观察

上线后重点看 4 个维度：

1. 写入成功率
2. 查询耗时
3. 数据完整性
4. 兼容性异常

推荐巡检项：

- 新表行数是否持续增长
- 外键引用是否存在孤儿数据
- `cache_hit` 比例是否异常
- 是否出现“有 run 无 result rows”
- 是否出现“有 template 无 version”

## SOP 7：回滚

回滚分三层：

### 应用回滚

新代码撤回，旧表还可继续读写。

### 读路径回滚

读逻辑切回旧表，但新表数据先不删。

### 写路径回滚

停止新表写入，但保留已写数据用于排查。

原则：

- 先停读切换，再停写
- 不在第一时间删新表数据
- 回滚不是清库

## 开放日模块的当前 DBA 重点

结合当前仓库，下一阶段最需要 DBA 主动守住的是这几件事：

### 1. 把“快照”改成“运行事件”

当前最大风险不是没有表，而是语义不准。

要把：

- “缓存结果”
- “历史快照”
- “用户测算动作”

三者彻底拆开。

### 2. 给方案建立稳定身份和版本

当前方案保存更像“另存一份新对象”。

下一步要改成：

- `scenario_template`
- `scenario_template_version`

这样业务变化再大，也不会丢历史。

### 3. 给数据集建立一等实体

当前很多信息还躺在 `command_json` 里。

这会导致：

- 难复用
- 难审计
- 难批量分析

所以 DBA 要推动：

- `upload_artifact`
- `dataset`
- `dataset_profile`

三层分开。

### 4. 给“人工修正”预留落点

像名称消歧、字段映射、sheet 选择、质量修正规则，这些如果进入日常流程，就不该只停留在前端内存。

一旦用户会反复用到，就应该考虑持久化：

- 映射模板
- 消歧决策
- 数据源解析画像

## 什么该正式持久化，什么不用

### 建议正式持久化

- 上传文件身份
- 解析后的数据集
- sheet 选择结果
- headers / mappings
- 质量报告
- 方案模板
- 方案版本
- 每次测算 run
- 逐行结果
- 逻辑护栏标签
- 人工消歧结果
- 导出产物

### 只建议做本地会话态

- 当前搜索词
- 当前选中行
- 当前侧栏折叠状态
- 当前全屏状态
- 提示文案
- 当前弹窗开关

### 介于中间，按产品决定

- 基准对比快照选择
- 最近使用的方案
- 最近使用的 sheet
- 最近使用的字段映射

如果目标是提升个人使用连续性，可以放浏览器本地；
如果目标是跨设备协同或审计，就应该进后端。

## DBA 每次评审 PR 的检查单

收到和持久化有关的 PR 时，逐项过一遍：

1. 有没有把缓存误当业务事实？
2. 新字段是不是其实应该新表？
3. 新对象是不是应该版本化？
4. 有没有唯一键 / 指纹防止重复写？
5. 有没有为未来查询留索引？
6. JSON 里有没有埋了本该结构化的字段？
7. 回放老数据会不会失真？
8. file fallback 和 Neon 语义是否尽量一致？
9. migration 是否可重复执行？
10. 回滚路径是否清楚？

## 推荐协作方式

DBA 和应用开发协作时，建议固定输出 3 份东西：

### 1. 变更说明

写清：

- 为什么改
- 改什么实体
- 新旧语义差异

### 2. 迁移说明

写清：

- 是否双写
- 是否回填
- 是否灰度
- 如何回滚

### 3. 查询说明

写清：

- 未来怎么查
- 靠什么索引
- 哪些字段必须结构化

## 最后的经验总结

一个会不断变的业务，数据库最怕的不是“字段不够”，而是：

- 事件和状态混了
- 当前值和历史值混了
- 缓存和事实混了
- DTO 和 schema 混了

DBA 真正的适应能力，不是改得快，而是每次变化来了都能先把这几层拆清楚，再决定怎么落库。

对这个项目来说，最重要的工作方法就是：

- 先稳实体
- 再稳事件
- 再稳版本
- 最后再谈缓存和 UI 便利性

只要这个顺序不乱，代码和业务再变，数据库也不会被带偏。
