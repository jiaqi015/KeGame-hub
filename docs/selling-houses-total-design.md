# 卖房（资产顾问）总设计

最后更新：2026-04-19

这份文档是给人看的“总设计稿”。

它不替代所有细文档。
它的作用是：

> 把现在已经设计出来的世界观、玩法、模型、引擎、页面、沉淀方式，收成一份能从头读到尾的总说明。

如果只想快速理解这套游戏怎么设计，先读这份。

当前实现层命名与最小字段合同，以 [selling-houses-implementation-contracts.md](/Users/jiaqi/Documents/开放日测算/docs/selling-houses-implementation-contracts.md) 为准。

## 0. 一句话总设计

这是一个二手房资产顾问经营游戏。

玩家扮演一个经纪人，不是简单点按钮卖房，而是在一个真实运转的房产市场里，同时经营多套房源、维护业主、推进客户、借助组织网络、对抗竞争，最后争取成交、守盘、业主满意和高分。

核心结构是：

```text
业务事实
  -> 世界模型
  -> 日结引擎
  -> 玩家动作 / Matter
  -> 页面投影
  -> 单局结算
  -> 游戏层沉淀 / 排行榜
```

---

## 1. 这个游戏到底在模拟什么

它模拟的不是“房子上架然后卖掉”。

它模拟的是：

> 在高库存、高客户量、长决策周期、低月成交率、强竞争、强协作的二手房市场里，经纪人怎么把一批盘经营出结果。

几个底层业务事实必须固定：

1. 房源多，成交少。
2. 客户多，但决策慢。
3. 客户会同时看很多房。
4. 房子之间的竞争，本质是争同一批客户。
5. 业主不是房子的字段，业主是独立主体。
6. 客户不是机会，客户和房子的关系才是机会。
7. 同 ACN 内房源公开、客户私有。
8. 同 ACN 更多是联卖，跨品牌才是明确竞争。
9. 市场有时间和空间，不是一个热度数字。
10. 玩家做的是事项经营，不是动作按钮连点。

---

## 2. 玩家目标

玩家一局里的目标不是单纯“卖最多套”。

更准确地说，玩家要同时做到三件事：

1. 把能卖的房尽量卖好。
2. 守住关键盘，不要被外部竞争打掉。
3. 让业主对过程和结果尽量满意。

所以评分采用三维：

```text
总分 = 能力分 + 守盘分 + 满意分
```

这能避免玩家只靠粗暴冲成交刷高分。

长期看，玩家会沉淀：

- 单局成绩
- 生涯统计
- 个人最好成绩
- 排行榜位置
- 顾问风格标签

---

## 3. 总体架构

整个系统分三层：

```text
游戏层
  用户、权限、跨局统计、排行榜、生涯沉淀

局内层
  GameRun、World、Actor、Relation、Matter、Event、Model

投影层
  给页面、复盘、结果、排行榜看的解释和摘要
```

最重要的边界是：

> 游戏层沉淀历史结果，局内层推进当前世界，投影层只负责讲人话。

排行榜不能反过来影响局内世界。
页面提示也不能反写底层真相。

## 4. 世界模型

局内世界的核心不是 `Case`，而是 `World`。

`World` 里有 5 类核心东西：

1. `Actor`
2. `Relation`
3. `Matter`
4. `Event`
5. `Model`

### 4.1 Actor

Actor 是世界里的主体：

- `Case`
- `Owner`
- `Customer`
- `Broker`
- `Brand`
- `Store`
- `BizAreaManager`
- `Rival`

注意：

- `Case` 是房子，不是上帝对象。
- `Owner` 是业主，不是房子的字段包。
- `Customer` 是客户，不是某套房的机会。
- `Broker` 是经纪人，玩家只是其中一个 Broker 的视角。

### 4.2 Relation

Relation 是两个主体之间持续存在的关系：

- `OwnerCaseRelation`
- `CustomerCaseRelation`
- `BrokerOwnerRelation`
- `BrokerCustomerRelation`
- `CoSaleRelation`

最关键的是：

> 机会不是客户自己，也不是房子自己，而是 `CustomerCaseRelation`。

同时，成交也不能只做成机会字段的一次改值。

> 成交是一条独立的 `ClosedDealRecord`，它记录谁和谁成交、哪个组织成交、房源端和客源端是谁。

### 4.3 Matter

Matter 是玩家正在推进的一件具体事。

例如：

- 周度反馈
- 竞品诊断
- 安排带看
- 推动开放日
- 谈底价
- 推进出价

动作只是 Matter 里的步骤。

### 4.4 Event

Event 是已经发生的事实。

例如：

- 客户完成首次看房
- 业主同意开放日
- 业主松口降价
- 客户被竞品吸走
- 开放日结束

事件是复盘、结果、回放、解释的基础。

### 4.5 Model

Model 是独立评估器：

- `MarketModel`
- `GoodHouseModel`
- `PriceModel`
- `CompetitionModel`
- `DealClosingModel`

它们不是页面文案，也不是某个主体的字段。

## 5. 房源、业主、客户怎么拆

### 5.1 房源

房源拆成：

- `CaseProfile`
  房子客观属性
- `CaseRuntime`
  当前市场表现

房源本身放：

- 小区
- 板块
- 户型
- 面积
- 朝向
- 楼层
- 标签
- 缺点

不放：

- 业主信任
- 客户意向
- 客户推进阶段
- 页面建议

### 5.2 业主

业主拆成：

- `OwnerProfile`
  出售动机、性格、价格态度
- `OwnerRuntimeState`
  焦虑、情绪、防御、理解市场程度
- `OwnerCaseRelation`
  这个业主卖这套房时的耐心、信任、配合、价格期待

### 5.3 客户

客户拆成：

- `CustomerProfile`
  预算、需求、区域偏好、决策风格
- `CustomerRuntimeState`
  活跃度、疲劳、紧迫度、注意力容量
- `BrokerCustomerRelation`
  经纪人和客户之间的信任、理解、联系深度
- `CustomerCaseRelation`
  客户和某套房的机会状态

从 Case 视角看客户池时，还要再分一层：

- 未见面客户只作为潜力池体量和画像展示。
- 已见面客户才进入实名机会和阶段管理。

这样房源页能看到“这套房还有多少潜在客群”，但不会把平台流量误当成真实机会。

### 5.4 成交

成交应该从机会里独立出来。

不能只写成：

```ts
// 错误示例：不要把正式成交塞回机会阶段
relation.stage = 'closed'
```

更稳的是三层：

- `CustomerCaseRelation`
  负责讲推进到哪
- `DealClosingEvaluation`
  负责讲今天有没有成交资格
- `ClosedDealRecord`
  负责讲这笔成交正式发生了，而且是谁和谁成交的

这样后面才能稳定回答：

- 一共成交几单
- 哪套房成交了
- 哪个客户成交了
- 是哪个品牌、门店、经纪人成交的
- 是自成交、联卖成交，还是跨品牌成交

## 6. 机会主线

机会阶段建议固定为：

```text
线上咨询
  -> 有意向
  -> 预约首次看房
  -> 看房
  -> 再次看房
  -> 见面
  -> 出价
```

还有两个异常状态：

- 停滞
- 流失

这里有一个非常重要的边界：

> 看房是阶段，自己来 / 开放日是进入看房的方式。

> 机会 canonical 到 `offer` 为止；正式成交由 `DealClosingEvaluation` / `ClosedDealRecord` 独立表达。

机会推进不是客户自己升级。

要算的是：

```text
P(advance CustomerCaseRelation)
```

主要输入是：

- 房子的吸引力
- 推广和跟进动作
- 客户需求和预算匹配
- 业主是否配合
- 价格是否挡住
- 竞品是否更强
- 近期是否有有效接触

## 7. 好房模型

好房分不是房子本身的静态分。

它是一个第三方客观评估器，回答：

> 在今天这个市场里，这套房整体好不好卖。

拆成三维：

```text
D1 准客池 / 客户需求
D2 房屋吸引力 / 产品力
D3 业主意愿 / 配合
```

也可以用更业务的话理解：

1. 有没有人愿意买。
2. 房子本身行不行。
3. 业主愿不愿意配合卖。

好房分不直接等于成交概率。
它是 `GoodHouseModelOutput / GoodHouseEvaluation` 里的模型评估结果，
不是 `Case` 的原始字段。
它会作为机会推进、经营优先级和页面表达的重要输入。

---

## 8. 价格模型

价格必须拆成三层：

1. `挂牌价`
   现在对外展示的价格。
2. `业主心理价`
   业主心里真正想卖的价格。
3. `市场估价`
   市场客观认为这套房值多少。

价格模型主要输出：

- 价格压力
- 价格差距
- 价格弹性
- 成交可行度
- 是否进入谈价窗口

关键判断：

> 很多时候不是房子没人要，而是价格站不住。

## 9. 市场与时间

市场不能只是一个热度数字。

市场至少有两条维度。

### 9.1 空间维度

```text
city
  -> district
  -> bizArea
  -> community / cluster
  -> segment
```

其中 `segment` 不是地理层，而是总价带、户型段、客户需求段。

### 9.2 时间维度

```text
年
季度
月
周
日
```

不同时间层含义不同：

- 年：大盘背景
- 季度：阶段行情
- 月：压力和松动窗口
- 周：行动编排
- 日：事实落账

还要区分：

- 城市时间
- 商圈时间
- 个人时间

城市时间决定大盘空气。
商圈时间决定局部流量和竞争。
个人时间决定今天先处理谁。

---

## 10. 组织、ACN、竞争、联卖

组织层建议是：

```text
BrokerageCompany
  -> Brand
    -> ACN
      -> Store
        -> BizAreaManager
        -> Broker
```

几个规则必须固定：

1. 经纪公司有品牌。
2. 每个品牌内部有 ACN。
3. 同 ACN 内房源公开。
4. 同 ACN 内客户私有。
5. 同 ACN 内主要是联卖。
6. 跨品牌才是明确竞争。
7. 联卖要分房源端和客源端。
8. 跨品牌成交你的房，算丢盘。
9. 跨品牌成交你的客户，算丢客。

竞争强度不是只看小区距离。

更本质看：

- 是否争同一批客户
- 是否同预算
- 是否同需求
- 是否同户型段
- 是否同商圈
- 是否同小区

## 11. 玩家动作和 Matter

玩家不是点动作按钮。

玩家是在推进 Matter。

Matter 四类模板：

1. `report`
   汇报型，比如周度反馈、带看反馈。
2. `diagnose`
   诊断型，比如竞品调研、客户池诊断。
3. `execute`
   执行型，比如带看、推广、开放日承接。
4. `negotiate`
   博弈型，比如谈底价、谈报价、推进出价。

动作分四类：

1. 沟通型
2. 运营型
3. 撮合型
4. 协同型

一次 Matter 可以包含多个动作。

例如开放日 Matter：

```text
和业主沟通开放日价值
  -> 向经理申请活动名额
  -> 做推广预热
  -> 承接开放日到访
  -> 给业主做活动反馈
```

## 12. 日结引擎

一天过去，不是简单重算。

它必须做五件事：

1. 模拟
2. 推理
3. 计算
4. 检查
5. 完成

推荐主链路：

```text
Step 0 结算当天遗留 Matter
Step 1 推进时间
Step 2 结算市场事件
Step 3 更新 CaseRuntime
Step 4 更新 Owner / OwnerCaseRelation
Step 5 更新 CustomerRuntimeState
Step 6 更新 CustomerCaseRelation
Step 7 更新 PriceModel
Step 8 更新 GoodHouseModel
Step 9 生成 Projection 和日结摘要
Step 10 做一致性检查
```

如果跳过 7 天，不是粗算一次。

应该是：

```text
连续跑 7 次 advanceDay()
```

这样周末、月底、Matter 到期、市场事件启停才不会丢。

## 13. Projection 页面投影

Projection 的职责是：

> 把世界真相翻译成玩家能判断的信息。

它不能反写世界。

核心投影包括：

- `DashboardProjection`
- `CaseDetailProjection`
- `CustomerDetailProjection`
- `MarketRadarProjection`
- `ActionReadinessProjection`
- `ReviewProjection`
- `ResultProjection`
- `LeaderboardProjection`

页面看到的：

- 当前主矛盾
- 适合谈价
- 客户池偏薄
- 本周适合开放日
- 输在承接没跟上

这些都是投影，不是底层真相。

投影文案必须遵守业务语言口径：

- 不能只说“风险升高”，要说是哪条事实导致风险升高。
- 不能只说“建议跟进”，要说跟谁、为什么、怎么跟。
- 不能只说“客户意向提升”，要说客户做了什么，才判断意向提升。

详细口径见 [selling-houses-business-language-guide.md](/Users/jiaqi/Documents/开放日测算/docs/selling-houses-business-language-guide.md)。

## 14. 信息架构

一级信息架构建议是：

```text
开局
经营概览
房源
客户
市场雷达
复盘
结果 / 排行榜
```

玩家真正玩的界面，建议是一个经营工作台：

```text
顶部：局内状态条
左侧：一级导航
中间：主工作区
右侧：洞察与行动侧栏
底部 / 抽屉：流水日志
```

信息层级固定为：

```text
L1 一级导航
  -> L2 页面视图
    -> L3 分区 / 列表
      -> L4 卡片 / 行
        -> Detail 详情页 / 详情抽屉
```

这几层职责不能混：

- 一级导航负责经营场景
- 页面视图负责判断问题
- 分区 / 列表负责定位对象
- 卡片 / 行负责摘要和点击入口
- 详情页负责解释、追因果和行动

必须支持三类流水：

- 全局流水
- 对象流水
- 日流水

新闻、事件、事实实体、日志要分清：

- 事实实体是世界里的对象
- 事件是某个时间点发生的事实
- 新闻是给玩家读的一组事件摘要
- 流水日志是按时间排列的事件记录

必须有详情的对象包括：

- 房源
- 客户
- 机会
- Matter
- 活动
- 新闻
- 事件
- 市场范围
- 组织 / 联卖关系

### 14.1 开局

解决：

- 打哪一档难度
- 这局什么压力
- 是标准局还是随机局

### 14.2 经营概览

核心是周日历。

显示：

- 今日新闻
- 今日事项
- 今日提醒
- 本周重点节点

它回答：

> 今天先处理谁。

### 14.3 房源

主战场。

回答：

- 这套房值不值得打
- 卡点在房、业主、客户、价格还是市场
- 当前先做什么 Matter

### 14.4 客户

推进辅助。

回答：

- 哪些客户值得推
- 哪个客户适合哪套房
- 谁快流失了

### 14.5 市场雷达

外部环境。

回答：

- 城市、区域、商圈、segment 哪里变了
- 这些变化打到我哪些盘
- 有没有联卖、竞品、开放日窗口

### 14.6 复盘

回答：

- 为什么赢
- 为什么输
- 哪一步是转折点

### 14.7 结果 / 排行榜

回答：

- 这局得分
- 三维表现
- 单房结局
- 榜单位置

## 15. 单局结算和跨局沉淀

一局结束后，先结算：

- 总分
- 能力分
- 守盘分
- 满意分
- 单房结局
- 成交数
- 守盘数
- 丢盘数
- 丢客数

然后沉淀到游戏层：

- `RunResult`
- `PlayerCareerStats`
- `LeaderboardEntry`

排行榜三类：

1. 总分榜
   看长期稳定高质量输出。
2. 单局最高榜
   看个人峰值。
3. 局数榜
   看投入和资历。

## 16. 难度和剧本

难度不能散落在各个规则里。

它应该是配置层：

```text
DifficultyTier
  -> DifficultyProfile
  -> RunDifficultyConfig
```

难度主要控制：

- 房源数
- 时间压力
- 关系脆弱度
- 市场压力
- 事件密度
- 竞争耦合度
- 资源紧张度

日结、生成、评分、结果页都应该读同一份 `RunDifficultyConfig`。

---

## 17. 第一阶段最小闭环

不要第一版就做全市场。

第一阶段建议只做一条纵向薄片：

```text
开局
  -> 生成一个小世界
  -> 6-8 套房
  -> 一个商圈
  -> 一个品牌 ACN
  -> 一批客户
  -> 玩家做 1-2 类 Matter
  -> 日结推进
  -> 客户机会变化
  -> 业主状态变化
  -> 房源表现变化
  -> 复盘解释
  -> 结算入榜
```

第一阶段最重要的是：

- 跑得通
- 解释得清
- 边界不乱

不要先追求所有模型都极其复杂。

---

## 18. 设计边界

这几条不能破：

1. `Case` 不能再变回上帝对象。
2. 客户画像、客户状态、机会状态不能混。
3. 业主画像、业主状态、业主卖这套房的关系不能混。
4. Matter 不能退化成按钮。
5. Event 不能退化成 UI 日志。
6. Projection 不能反写世界。
7. 排行榜不能影响局内世界。
8. 同 ACN 联卖和跨品牌竞争不能混。
9. 市场事件不能直接跳到最终结果。
10. 概率必须建立在 readiness 上，不能裸骰子。
11. 页面文案、事件描述、系统建议不能写成 AI 总结，必须绑定业务事实、对象、动作、影响和下一步。

## 19. 后续扩展方向

这套架构后面可以扩：

1. 更多城市和商圈
2. 更多品牌和 ACN
3. 更复杂的 Rival policy
4. 更细的业主和客户类型
5. 更多 Matter 模板
6. 更细的开放日和活动系统
7. 赛季排行榜
8. AI 复盘
9. 多角色视角

但扩展顺序建议是：

> 先跑通单局闭环，再加市场复杂度，再加组织复杂度，最后加长期竞技和社交。

---

## 20. 最后一句

这套总设计最核心的判断是：

> 卖房不是一个“成交按钮”游戏，而是一个多主体、多关系、多时间、多事件共同驱动的经营世界。

只要守住：

- 主体归主体
- 关系归关系
- 事项归事项
- 事实归事件
- 展示归投影

这个游戏后面就能不断加深，而不会重新塌回一个大 `Case` 对象。
